## 一、项目起源与核心思考

### 1.1 为什么做这个项目

Harness-Flow 最初是我为解决个人开发效率瓶颈而打造的工具。在使用 AI 辅助编程的过程中，我发现了两个反复出现的痛点：

**痛点 1：AI 缺乏工程纪律。** 没有结构化约束时，Agent 容易跳过需求分析直接写代码，或者写完功能忘记写测试、写文档。这种"先开枪再瞄准"的模式在探索性编程中尚可接受，但在严肃的软件工程中会产生大量技术债务。

**痛点 2：Token 成本与产出质量不匹配。** 所有开发阶段使用同一个模型，结果是：要么设计阶段因模型能力不足导致架构缺陷，要么编码阶段因模型过于昂贵造成浪费。实际上，不同阶段对模型能力的需求差异极大。

### 1.2 核心设计理念

基于以上观察，我确定了两个核心设计原则：

**原则 1：流程强制管控，Agent 自由发挥。** 用 Python 在框架层面强制 5 阶段工作流——头脑风暴（需求澄清）→ 规划（架构设计）→ 编码（执行实现）→ 评审（质量审计）→ 归档（总结沉淀）。每个阶段配有标准化的 Markdown 模板作为 Skill 指南，Agent 在模板框架内自由发挥。Hooks 门禁确保每个阶段的产出合规后才能进入下一阶段。

**原则 2：差异化模型策略——贵模型做设计，便宜模型写代码。** 通过 `config.yaml` 的角色化配置，不同阶段可以绑定不同的 Agent 类型和模型：

| 阶段 | 角色 | 模型策略 | 原因 |
|------|------|---------|------|
| 头脑风暴 | analyst | 高能力模型 | 需求澄清需要深度推理和结构化提问 |
| 规划 | architect | 高能力模型 | 架构设计是软件质量的根基，不能省 |
| 编码 | developer | 低成本模型 | 只要设计足够清晰，编码就是翻译工作 |
| 评审 | reviewer | 中等模型 | 需要一定的代码理解能力 |
| 归档 | archivist | 低成本模型 | 文档整理是简单的总结性工作 |

这个策略的核心洞察是：**设计质量决定了编码的难度下限**。一份好的设计文档（数据模型、接口定义、路由规划）本质上就是编码的精确说明书，低能力模型完全可以胜任"照图施工"的工作。这种分层策略在保持产出的同时，将 Token 消耗降低了 40-60%。

### 1.3 与 Atoms 的巧合

Harness-Flow 从第一天起就承载了我对"AI 驱动软件工程"的期待。看到 ROOT 的笔试挑战时，我发现这个方向与 Atoms 的核心理念不谋而合。项目原本是纯命令行 TUI 交互形态，Web UI 和「一键部署 + Cloudflare Tunnel 公网访问」是本次为 Demo 新增的能力，恰好补全了「可视化展示」和「可测试访问」两个关键环节。

## 二、实现思路与关键取舍

### 2.1 架构关键取舍

| 决策 | 选择 | 理由 | 舍弃的替代方案 |
|------|------|------|---------------|
| **后端语言** | Python | 快速原型验证，Rich 生态的 TUI，FastAPI 的异步支持 | Node.js（生态好但 TUI 弱），Go（性能好但迭代慢） |
| **Agent 通信** | 多后端插件（Gemini/OpenCode/PTY/Mock） | 不绑定单一 AI 供应商，可切换、可 Mock 测试 | 单一 Agent SDK 深度绑定 |
| **Web 前端** | FastAPI + Jinja2 + HTMX | 服务端渲染，零前端构建，HTMX 提供 SPA 级交互 | React/Vue SPA（过度工程），纯 SSR（交互不足） |
| **实时通信** | SSE (Server-Sent Events) | 单向流式推送足够，比 WebSocket 简单 | WebSocket（双向但不必要），Polling（延迟高） |
| **数据持久化** | JSON 文件 (.state) + STATUS.json 看板 | 零依赖，人类可读，易调试，Git 可追踪 | SQLite/PostgreSQL（引入 ORM 复杂度） |
| **部署方案** | Cloudflare Tunnel | 零配置公网穿透，无需购买域名/服务器 | Vercel/Railway（需额外账户），ngrok（不稳定） |
| **UI 风格** | 暗色终端风格控制台（Web）+ Rich 三栏布局（TUI） | 模拟真实开发环境，降低认知负担 | 传统 Dashboard 风格（与核心体验不匹配） |

### 2.2 与 Atoms 的对标设计

| Atoms 概念 | Harness-Flow 实现 |
|-------------|-------------------|
| Agent 工作流 | 5 阶段生命周期，Stage Hooks 门禁 |
| 代码生成 | AI Agent 在 `repo/` 目录下创建完整项目（已生成 Spring Boot + Hexagonal 架构示例） |
| 可视化展示 | Web Dashboard 实时展示任务状态 + Agent 日志流 + 部署预览 |
| 部署预览 | 一键部署 + Cloudflare Tunnel 公网 URL |
| 交互控制 | Web SSE 实时对话控制台 + TUI 命令式操作 |

## 四、未来扩展方向与优先级

基于当前完成度和实际使用反馈，以下是重新排序的优化路线图：

### P0 — 交互与体验优化（预计 6-8h）

> **为什么是 P0**：直接影响 Demo 的第一印象和使用流畅度，是"可用"到"好用"的质变。

1. **探索与 Agent 更好的交互方式** — 当前"一次命令一次回复"（one command one question）的串行交互效率较低，尤其在复杂需求场景下需要多轮来回才能完成意图对齐。计划探索：预设选项快速回复减少打字成本、意图模板一键注入减少重复描述、Agent 对话的分支可视化（类似思维导图），以及支持在单轮交互中完成多步骤指令（如"设计用户模块 + 生成接口文档 + 创建数据库 schema"一条命令全部完成）。
2. **上下文管理优化** — 当前 PromptBuilder 将所有前序产出全量注入，随着阶段推进会产生大量冗余上下文。计划引入：上下文摘要压缩、关键信息提取（只注入当前阶段需要的部分）、滑动窗口截断策略。

### P1 — 工程能力扩展（预计 10-14h）

> **为什么是 P1**：让 Harness-Flow 从 Demo 工具变成可真实用于日常开发的生产力工具。

3. **多任务并行支持** — 当前单任务引擎设计导致无法同时推进多个项目。计划引入 Git Worktree 为每个任务创建隔离的工作目录，结合 Docker 容器提供更彻底的运行环境隔离。技术路径：`git worktree add` + `docker run --volumes-from`。
4. **CI/CD 集成** — 将 Harness-Flow 嵌入 GitHub Actions 流水线，实现 Push 触发自动 Code Review、自动测试、自动部署。让 Agent 成为 CI/CD 的一个可编排步骤。
5. **Agent 生态扩展** — 当前支持 4 种 Agent 后端（OpenCode / Gemini / PTY / Mock），计划扩展支持更多 AI 后端：Claude API（Anthropic）、本地模型（Ollama / LM Studio）、Cursor Agent 等。不同后端的接入可以进一步丰富"贵模型做设计、便宜模型写代码"的策略选择。

### P2 — 架构深度强化（预计 10-15h）

> **为什么是 P2**：解决高复杂度项目的根本性瓶颈，但改动成本高，需在 P0/P1 稳定后进行。

5. **复杂项目的工作流增强** — 当前的 Markdown 模板 + 线性阶段推进在应对单体 CRUD 时足够，但面对微服务、多模块项目时力不从心。计划引入：子任务拆分机制（一个 Task 可 spawn 多个 SubTask）、依赖图管理（Task A 完成后自动触发 Task B）、跨任务上下文共享。

### P3 — 产品化与生态

6. **Docker 一键部署** — `docker run` 启动完整环境，降低使用门槛。
7. **应用模板市场** — 预设常见应用骨架（Todo App / 博客 / Dashboard），用户选择后一键生成。
8. **协作功能** — 多人共享任务看板，实时同步 Agent 状态。
9. **SaaS 化部署** — 多租户隔离、用量统计与计费。

## 五、技术亮点

1. **差异化模型策略**：贵模型做设计、便宜模型写代码，通过 `config.yaml` 的角色化配置实现了 Token 消耗与产出质量的最优平衡。

2. **阶段合规性门禁 (Hooks)**：Soft Check（Markdown 模板校验）+ Hard Check（Shell 脚本验证）的双重门禁确保 AI 产出质量，防止"只写代码不做检查"。

3. **插件化 Agent 架构**：AgentFactory 实现 `类型名 → 具体实现` 的插件式注册，新增 Agent 类型只需实现 BaseAgent 抽象类，零侵入现有代码。

4. **SSE 事件协议**：5 种事件类型（log/question/settlement/status/state）覆盖 AI Agent 与人协作的全交互模式，协议清晰、可扩展。

5. **TUI 智能模式识别**：基于正则引擎自动分析 Agent 输出，识别 yes/no 确认、选项列表、结构化提问，切换输入模式。用户无需手动切换交互方式。

6. **零前端构建**：HTMX + SSE + Vanilla JS 的组合实现 SPA 级交互体验，无需任何前端构建工具，代码即部署。

7. **双模交互**：终端 TUI（Rich 三栏布局）+ Web Dashboard（HTMX + SSE）共享同一套引擎，满足不同场景下的使用需求。
