# 闭环：从错误中学习的三种入口

> 本仓库的 bug 极少是"漏了一个 case"，绝大多数是**判据量错了地方**。
> 修掉一个实例后，兄弟实例留在原地，下次以另一副面孔复发。
> 从已经犯过的错误中总结出可枚举的形状，不让同一个形状第七次出现。

## 闭环结构

```
  需求 → 设计                  ← 复盘
    │                            │
    │  Entry A                   │  Entry C
    │  新增门禁前                 │  bug 修完复盘
    │  查形状库、走五问           │  更新形状库
    │                            │
    ▼                            │
  ┌──────────────────────────────┘
  │
  │  Entry B
  │  bug 处理中
  │  分类 → 扫兄弟 → 修全部
  ▼
  修复 → 验证 → 复盘
```

三条入口，缺一条则循环不闭合：

| 入口 | 时机 | 防止什么 |
|---|---|---|
| **Entry A** | 写新判据 / 新门禁之前 | 设计时重复已知错误形状 |
| **Entry B** | 修 bug 的过程中 | 修掉一个实例，兄弟留在原地 |
| **Entry C** | bug 确认修完之后 | 知识丢失，下次重蹈覆辙 |

## 形状库

每条判例归入一个形状。形状是**可枚举的缺陷类别**，写在文件里
（而不是散在 git log 和 A0 的散文里），新增判据前必须查一遍。

### 形状速查表

| 编号 | 一句话 | 典型症状 | 检测方法 |
|---|---|---|---|
| **S1** | 取样点少于落点 | 产出优秀，门禁判"空转" | 枚举所有可能的产出落点，判据量了其中几个 |
| **S2** | 阶段错位 | 硬阻断，但没有角色能满足它 | 判据要求的动作，在哪个阶段、哪个角色有权限做 |
| **S3** | 只有下界 | 无限循环，无终止条件 | 每个数字约束，是否同时有上界和可执行的终止动作 |
| **S4** | 执行环境错位 | 两侧结论相反，但都没说谎 | 门禁和 agent 的 cwd、解释器、PYTHONPATH 是否一致 |
| **S5** | 判据恒真 | 模板自带标题、硬编码 True | 判据在 agent 什么都没做的情况下是否也会通过 |
| **S6** | 没发生当通过 | 线程内异常静默、模型未调用工具 | 是"真实发生了某个结果"还是"什么都没发生" |
| **S7** | 判据存在无人调用 | 字段定义了、函数写了、零消费方 | 用 rg 查生产调用点，排除测试和定义 |
| **S8** | 一个语义两个数字 | 改 A 必须改 B，否则对不上 | 两个硬编码常数的语义是否相同，是否从同一源头推导 |
| **S9** | 前提变了没跟上 | 修 A 时 B 坏，但 B 跟 A 不直接相关 | 本次改动是否改变了某个隐式前提，所有依赖该前提的代码是否已更新 |
| **S10** | 修了一半 | 同一形状在其他位置还在 | 根因是形状而非位置，找所有同形状实例 |
| **S11** | 判据的输入或时机由被判者控制 | 「你没写 X」，而真正断的是上游某个动作 | 判据读的东西是谁写的？判据什么时候触发，由谁决定？ |

#### S2: 阶段错位

| 实例 | 任务 | 现场 | 根因 | 提交 |
|---|---|---|---|---|
| 1 | helloworld | prompt 说"用 write_file 回填模板"，权限层 deny workspace/** | 指令与约束各自独立，互不校验 | c0b7338 (第 2 条) |

#### S5: 判据恒真

| 实例 | 任务 | 现场 | 根因 | 提交 |
|---|---|---|---|---|
| 1 | helloworld | check_02 只 `grep -q "## Task DAG"`，该标题是模板自带的 | 判据量的是模板，不是 agent 产出 | c0b7338 (第 4 条) |
| 2 | helloworld | e2e verify.py 的 ok 参数硬编码字面量 True | 写测试时把判据写成恒真 | c0b7338 (第 7 条) |
| 3 | rrr 近失 | 回落模板区时若直接量整篇，模板自带样板合计已超阈值 80 | 用 `_added_lines` 逐行相消，只算 agent 真正添进去的行 | 3ab28a9 |

**近失**（第 3 例）被 `_added_lines` 挡在门外，没有真正进入生产路径。用它作为判例是因为它说明了"S5 的常见成因"：简单地把范围扩大就会让判据自动变绿。

**检测**：`rg -n "ok\s*=\s*True|return True|passed\s*=" sw_lib/workflow/ hooks/ tests/` 扫出来，确认不是恒真。

#### S6: 没发生当通过

| 实例 | 任务 | 现场 | 根因 | 提交 |
|---|---|---|---|---|
| 1 | 验收 15 | 模型没调用 write，文件没变，于是判"deny 有效" | 把"没发生"读成"被拦住" | 2.9.5 (第 4 条教训) |

| 实例 | 任务 | 现场 | 根因 | 提交 |
|---|---|---|---|---|

#### S8: 一个语义两个数字

| 实例 | 任务 | 现场 | 根因 | 提交 |
|---|---|---|---|---|
| 1 | ask_user | IDLE_TIMEOUT 混了"agent 卡住"和"等真人回答"两个语义 | 两个含义挤在一个常数里，通过数值关系掩盖混淆 | 2.9.13 |
| 2 | ask_user | opencode 路径 180s，Toolbox 路径 300s | 同一个语义，两个硬编码，各写一处 | 2.9.13 顺手修 |

#### S9: 前提变了没跟上

| 实例 | 任务 | 现场 | 根因 | 提交 |
|---|---|---|---|---|
| 1 | rrr | 放行阶段文件写权限后，判据"产出只在围栏区"的前提不成立了 | 修 A 时没检查所有依赖该前提的代码 | 3ab28a9 |
| 2 | qqqq 第 1 条 | 同上——claims 只读围栏区的前提失效 | 与 S1 实例 2 是同一件事，从不同视角描述 | a4205d1 |

#### S10: 修了一半

| 实例 | 任务 | 现场 | 根因 | 提交 |
|---|---|---|---|---|
| 1 | D0-1 | 十余处 `read_state→改→write_state` 调用点，只修了瓶颈处的单次写入 | 修复只覆盖了直接路径，同形状调用点未全部修复 | 2.8 |
| 2 | ppppp | 删掉 write 指令时，连同终止动作一起删了 | 修的是"做不到的事情"，但没检查被删的东西还承担了什么角色 | e791960 |
| 3 | ask_user | 把 QUESTION_TIMEOUT 从常量改成配置，破坏了测试覆写模式 | 参数化时没保留实例级逃逸口 | 2.9.13 |
| 4 | 多个 | 模板只有 01 修了落盘指令，02 同形状问题漏了 | 修 A 时不记得 B 和 A 形状相同 | 2.9.9 (第 2 条) |
| 5 | 44444 | 修 03 的 prompt 顺序时，另外四个阶段的 yaml 同样是 `{global_rules}` 打头 | 位置由五份 yaml 各自决定，改一份不改结构 | 2.9.19 |

**检测**：修完一个实例后，用 `same-shape-sweep` 技能扫同名形状的其他候选。

**2.9.19 的处置示范**：实例 5 没有"逐个改五份 yaml"，而是把位置**收归
`PromptBuilder`** —— yaml 不再自己摆放占位符。逐个改能让当下五个实例变绿，
但第六个阶段照旧会写在开头；收归一处之后这个形状**没有第六个实例可长**。
修 S10 时优先问："能不能让这个形状不可表达？"

#### S11: 判据的输入或时机由被判者控制

| 实例 | 任务 | 现场 | 根因 | 提交 |
|---|---|---|---|---|
| 1 | maybework / 7090 / ppppp | 三个任务收到同一句「❌ 未给出歧义分数」，根因分别是正则太窄、阶段没走完、提问无收敛出口 | 歧义分数是 agent **自评**，不写就读不到，门禁只能报「你没写 X」 | 2.9.17 |
| 2 | 7090 | agent 在**正文**里问「你同意方案 A 吗」，harness 收不到 question 事件，判定「说完了」→ 弹门禁 → 量一个尚未产生的产出 | 判据的**触发时机**也由被判者控制 | 2.9.18 部分修复：`decisions == 0` 硬拦。「问过但没问完」仍未覆盖 |
| 3 | 02-planning | `grep -q "## Task DAG"` / `"## Test Strategy"` —— 标题是 agent 写的 | 与 S5 实例 1 同源，从「谁提供输入」的视角看是 S11 | 未修，见下方登记 |
| 4 | 04-review | `grep -q "## Security"`、Reroute Evidence 表非占位符 | 同上 | 未修，见下方登记 |

**本轮 sweep 的处置**（2.9.17）：实例 1 已修（自评降级为参考 + 留痕 +
正则接纳中文动词）。实例 2 属 A13 第一道判据，是**另一个缺陷**（阶段完成性
不可判），不是本形状的同一实例，登记延后。实例 3、4 的**区分性质**：
它们背后都有硬规则兜底（`output_check._substance_report` 量的是围栏区实质
内容，04 另有 O1-O6 客观轨），grep 只是结构完整性检查，删掉它们不会让
空转过闸；且 A13 的 5.1/5.2 已把「降级为提示」写进落地顺序第 3 步，
与本轮「不一次全改准出语义」的判断一致（一次动四个阶段会让回归面失控）。

**2.9.18 的补充处置**：实例 2 已部分修复 —— `decisions == 0` 硬拦，
用纯证据（`record_decision` 只在用户实际回答时写入）而非文本启发式。
**未覆盖的那一半**：「问过 5 轮但最后一次追问没走 question 工具」，
要抓它需要会话层的「最后一次发言之后有无 question 事件」，属另一个数据源。
被否决的方案是判断产出区结尾是否问句 —— 那仍是读 agent 写的文本，
与实例 1 同一个错。**判据不该第三次栽在同一个形状上。**

**检测**：对每条判据问两句 —— 它读的东西是谁写的？它什么时候触发，由谁决定？
两个答案里只要有一个是「被判者」，就是 S11。

## Entry A: 写新判据/新门禁之前

> 防止设计时重复已知错误形状。

### 前置检查清单

```
[ ] 形状库速查 —— 逐个对 S1-S10，当前需求是否匹配某个已知形状
[ ] 如果匹配：该形状的判例中，哪条教训直接适用于本次设计？
[ ] 如果不匹配：是否已有足够的区分度说明"这不是已有形状的新实例"？
[ ] 五问（criterion-design 技能）逐条回答
[ ] wiring check 计划的消费方已确认（不是"写了之后再说"）
[ ] 三态设计：unavailable 有独立路径，不和 pass 混
[ ] 失败信息包含下一步：什么角色、在哪个阶段、做什么
```

### 输出

在设计文档或 commit 中留下：

```
# 形状检查
匹配形状: S? / 无匹配
判例参考: 2.9.x (相关实例)
五问结论: Q1=... Q2=... Q3=... Q4=... Q5=...
```

## Entry B: 修 bug 的过程中

> 防止修掉一个实例，兄弟留在原地。

### 流程

1. **定位根因** —— 先判断缺陷属于哪一类
   - 如果判据与事实矛盾 → criterion-design 技能
   - 如果感觉眼熟或之前修过类似的 → same-shape-sweep 技能
   - 如果以上都不是 → systematic-debugging 技能
2. **命名形状** —— 用形状库的编号，或新命名
3. **扫兄弟** —— 按形状签名的机械搜索，而不是靠记忆
4. **修全部** —— 同一形状的实例在同一个 commit 里修，或显式登记待办
5. **验证** ——
   - 单元测试通过
   - 真实任务目录上走一遍（"单元全绿 ≠ 机制接通"已发生六次）
   - 三类判据写全：新形状的测试 + 旧形状的回归 + 空转检测

### 形状命名规则

- 已有形状：用编号（S1-S10）
- 新形状：用一句话描述，不超过 20 字，写在 `docs/design/CLOSED-LOOP.md` 的形状库末

## Entry C: bug 修完复盘

> 防止知识丢失，下次重蹈覆辙。

### 复盘模板

```
## 形状: <编号或一句话>

## 提交: <commit hash>

### 现场
<两到三句话描述现场现象>

### 根因
<一句话说明根因，不包含文件名>

### 形状归属
<匹配已有形状 / 新形状>

### 判例
<如果匹配已有形状：第 N 次出现>
<如果新形状：新增到形状库>

### 兄弟
<同形状的实例：已修 / 已登记 / 排除>
<排除的需写明区分特征>

### 检测方法
<后人如何用 grep 或流程防止这个形状再次通过>

### 修复是否改变了某个隐式前提？
<是 / 否>

### 三态验证
- [ ] 单元测试通过（计数：___ passed）
- [ ] 真实任务目录通过（任务名：___）

```

1. 复盘文档写入 `docs/design/A0-state-integrity.md` 的 2.9.x 节
2. 形状库索引更新（如果新形状）
3. 技能更新（如果新形状的检测方法可以自动化）

## `scripts/orphan_criteria.py`

> 技能 `harness-criterion-design` 的最后一步一直要求跑这个脚本，
> 而它此前并不存在 —— S7 犯在了技能自己身上，这是该形状的第三个实例。
> 现已创建：[scripts/orphan_criteria.py](../../scripts/orphan_criteria.py)。

脚本维护一份「形状库登记判据」清单，逐个在生产路径
（`sw_lib` / `hooks` / `bin` / `sw` / `templates` / `config`）里找调用点，
排除 `tests/` 与 `docs/`，并跳过定义行本身。

```bash
python3 scripts/orphan_criteria.py
```

退出码：0 全部有消费方，1 存在孤儿判据，2 `rg` 不可用（按三态记 ❓，不算通过）。

首次实跑（2026-09-03）扫 19 个判据，命中一个孤儿：

```text
  ❌ is_idle                                S7  零生产调用点  (判例 2.9.9)
判据存在、无人调用：1 个
```

与 2.9.9 第 1 条登记的未修项一致 —— `transport.py` 的 `is_idle()`
至今只有定义与测试。脚本没有发现新问题，但它把一条靠人记住的待办
变成了每次可复跑的判定。

新增判据后应把名字加进 `REGISTERED_CRITERIA`，否则脚本扫不到它。
这一步本身也是 S7 的风险点：登记表漏登记，等于判据不在监控范围内。

## 与 DEV-PROTOCOL 的关系

本闭环不是对 DEV-PROTOCOL 的替代，而是补充。DEV-PROTOCOL 规定了**怎么做**，
本闭环规定了**做之前先查什么**和**做完之后还差什么**。

| 协议 | 规定 |
|---|---|
| DEV-PROTOCOL 第 1 节 | 红绿六步，不得跳步 |
| DEV-PROTOCOL 第 2 节 | 三态报告，不得二态化 |
| DEV-PROTOCOL 第 3 节 | 自循环纪律，判据在循环外 |
| **本闭环** | **写新判据前查形状，修完 bug 后更新形状** |
