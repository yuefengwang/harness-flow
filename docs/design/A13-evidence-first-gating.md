## 1. 这条原则本项目已经兑现过一次

A2 的第一句话是全仓库最硬的一条设计原则：

> **红不是 agent 声称的状态，是 harness 亲自观测并留痕的事件。**

03-coding 完全按它建成：harness 自己跑 pytest、自己读退出码与节点表。
任务 8090 的 agent 声称「23 个测试全部通过」，门禁照样拦下 —— 因为判据
从不问 agent 测试过没过，它自己去看。

**但这条原则只在 03 兑现了。** 01、02、04、05 的判据大量在读 agent
自己写的文本。同一个仓库里存在两套准出哲学，这才是「按下葫芦浮起瓢」的
结构性成因：修好的是 03 那一套，出问题的总是另一套。

## 2. 判据的两种性质：证据 vs 自述

判据的可信度不取决于它检查得多严，而取决于**它的输入由谁产生**。

| | **证据（evidence）** | **自述（self-report）** |
|---|---|---|
| 产生者 | harness 观测到的事件 | agent 写出来的内容 |
| 能否伪造 | 不能（判据区 deny + HMAC） | 能（写什么都行） |
| 能否跳过 | 不能（事件发生了就有记录） | 能（不写即可） |
| 典型 | pytest 退出码、`decisions`、`gate.signed_at`、git diff | 歧义分数、`## Task DAG` 标题、Security 章节 |

**关键区别不是「准不准」，是「能不能不写」。** 自述判据有一个共同的
失败模式：agent 不写，判据就读不到，于是门禁只能说「你没写 X」——
而真正的问题往往不是「忘了写」，是**上游有个动作没发生**。

### 全项目现状盘点（2026-09-03 实测）

| 阶段 | 判据 | 性质 | 备注 |
|---|---|---|---|
| 01 | `gate` 已签署 | ✅ 证据 | 用户在 TUI 点击，`signed_by`/`signed_at` |
| 01 | 产出区实质内容 ≥ 80 字符 | ⚠️ 半证据 | 围栏 nonce 由 harness 签发，但内容是 agent 写的 |
| 01 | **歧义分数 ≥ 8** | ❌ 自述 | agent 自评，不写就读不到 —— 任务 7090 卡死于此 |
| 02 | `grep "## Task DAG"` | ❌ 自述 | 标题是 agent 写的 |
| 02 | `grep "## Test Strategy"` | ❌ 自述 | 同上 |
| 03 | pytest 退出码 + 节点表 | ✅ 证据 | A2，harness 亲自执行 |
| 03 | 测试文件哈希冻结 | ✅ 证据 | harness 计算 |
| 03 | 缺依赖诊断 | ✅ 证据 | 读 requirements + importlib.metadata |
| 04 | O2/O3 测试事实 | ✅ 证据 | A6 客观轨 |
| 04 | O5 改动范围 | ✅ 证据 | git diff |
| 04 | O6 README | ✅ 证据 | 文件系统 |
| 04 | `grep "## Security"` | ❌ 自述 | 章节标题 |

**证据判据 8 条，自述判据 6 条。** 出过死锁的阶段（01 的 7090、
02 的 helloworld、04 的 qqqq）全部集中在自述那一侧。

## 3. 任务 7090 暴露的第二个问题：判据的**时机**也由 agent 控制

7090 不只是「分数没写」。日志 `14:52:32`：agent 输出
「**推荐方案 A**……你同意方案 A 吗？」然后结束发言 —— 它把问题写在
**正文里**，而不是调 `question` 工具（prompt 第 2 条明令禁止的做法）。

于是链条这样断掉：

```
agent 用正文提问
  → harness 收不到 question 事件
  → 判定「agent 说完了」
  → TUI 弹出门禁签署
  → 用户批准（界面就是这么请求的，不是用户的错）
  → 门禁去量一个尚未产生的产出
  → ❌ 未给出歧义分数
```

`.state` 里 `stage_status` 至今是 `running`。**这个阶段从来没完成过，
门禁却已经判过了。**

> **判例**：判据的输入由被判者提供已经很危险，判据的**触发时机**也由
> 被判者控制，则门禁形同虚设 —— 它只会在错误的时刻测量错误的东西，
> 然后报出一个指向错误方向的原因。

## 4. 设计：两道判据，先问「走完了吗」再问「达标了吗」

现在 01 只有一道判据，它把两个问题混在一起问，所以答错了也说不清。

### 4.1 第一道：阶段完成性（纯证据，harness 自主）

新增 `sw_lib/workflow/stage_completion.py`，只读 harness 自己写的事实：

| 事实 | 来源 | 谁写的 |
|---|---|---|
| `decisions` 轮次与回答 | `.state` | `record_decision`，仅 TUI 在用户实际回答时调用 |
| `stage_status` | `.state` | harness 的阶段机 |
| 产出区是否存在且非空 | 围栏 nonce | harness 签发围栏并落盘 |
| agent 最后一次工具调用类型 | `.log` / 会话事件 | harness 记录 |

**判定「阶段尚未结束」的证据组合**（任一成立即拦，且**不问 agent**）：

- `decisions` 为 0 条 —— 一轮都没问，01 的语义不成立；
- 产出区为空 —— agent 什么都没说；
- 最后一次 agent 发言以问句结尾**且**其后无 `question` 事件 ——
  它在等回答，不是说完了（7090 的形状）。

第三条是唯一带启发式的，因此它**只降级不硬拦**：判为
「阶段可能未结束」，`unavailable`（❓），并在 TUI 上把门禁按钮
从「批准」改成「agent 似乎在等你回答 —— 仍要签署？」。
误报的代价是多问用户一句，漏报的代价是 7090 那种死锁。

### 4.2 第二道：产出达标（证据为主，自评为辅）

只有第一道通过，才问第二道。此时歧义分数仍然读，但它的**地位变了**：

```
硬规则（决定性）      自评（参考）
────────────────      ──────────
decisions ≥ 1         歧义分数 ≥ 8
产出区 ≥ 80 字符
产出区非占位符
```

- **硬规则不满足** → ❌ 拦下，失败信息指向缺失的那个证据；
- **硬规则满足、自评缺失** → ❓ `unavailable`，**放行但记账**：
  下游报告该项记 ❓ 而非 ✅（与 A2 的 `--abandon-witness`、
  非 Python 栈让路同一条纪律）；
- **硬规则满足、自评 < 8** → ⚠️ 提示继续澄清，但**不硬拦** ——
  分数是 agent 对语义的判断，它有参考价值，但不该有一票否决权。

> **为什么自评降级而不是删掉**：agent 才知道「还有什么没问清」，
> 这个判断 harness 做不出来。删掉它等于丢掉唯一的语义信号。
> 但它不能是决定性因素 —— 那等于把准出开关交给被判者。

### 4.3 这个调整不会放松准出

有人会问：把分数从硬拦降级，7090 那种「问了 5 轮就想走」不就过闸了？

不会。7090 会被**第一道**拦下（agent 在等回答，阶段未结束），
而且失败信息说的是真话：

```
❓ 阶段可能尚未结束 —— agent 最后一次发言是问句，但未调用 question 工具
   已记录 5 轮问答，产出区 360 字符
   下一步：在 TUI 中回复 agent 的问题，或让它调用 question 工具重新提问
   若确认设计已定稿，仍可签署门禁（本项将记为 ❓）
```

对照现在的输出「请在产出里写明：`歧义分数：<0-10>`」—— 后者会把人
推去让 agent 补一个数字，而真正没做完的是这一轮对话。

## 5. 同一原则在其它阶段的应用

### 5.1 02-planning：`grep "## Task DAG"` 换成结构证据

标题是 agent 写的，写一行 `## Task DAG` 就能过 —— 这正是 2.9.7 判过的
「判据恒真」（`check_02` 那次）。既有的 `output_check._substance_report`
已经在量实质内容，`grep` 那两条应当**降级为提示**，硬判据交给产出区实质性。

更强的做法是让 02 的产出**结构化落盘**（DAG 写进 `.state` 的
`stages.02-planning.dag`，由 harness 解析并校验节点数与依赖成环），
但那要改 prompt 与工具契约，属另一个任务。

### 5.2 04-review：Security 章节与 Reroute Evidence

O1-O6 客观轨已经是证据判据。剩下两条 grep（`## Security`、
Reroute Evidence 表非占位符）是自述，且 Reroute 那条已经出过
「表里全是 `___`」的形态。同 5.1 处置：降级为提示，硬判据以 O 系列为准。

### 5.3 05-archive

`## Memory` / `## Retro` 已经只是警告（`echo "⚠️"`），未硬拦，符合本原则。
git 状态检查是证据判据，保留。

## 6. 落地顺序（建议）

分三步，每步独立可回滚：

1. **只加不改**：新增 `stage_completion.py` 与它的判定，先**只打印不拦**，
   在真实任务上跑一段时间，看它对 7090 这类现场的判定准不准。
   这一步零风险 —— 它不改变任何准出结论。
2. **接线 01**：第一道判据生效（`decisions == 0` 与产出区为空硬拦，
   问句启发式记 ❓），歧义分数同时降级为参考。
3. **推广 02/04**：grep 判据降级为提示。

**不建议一次全改。** 本仓库的历史教训是「两侧一起修」，但那说的是
*同一个形状*的两个实例；这里是四个阶段的准出语义，一次全动会让
回归面失控 —— 而准出判据一旦放松出错，代价是坏代码过闸。

## 8. 未决问题（需用户拍板）

1. **问句启发式的边界**：以问号结尾就算「在等回答」吗？agent 完全可能在
   总结里写反问句。备选：只在「问号结尾 **且** 本轮无 `question` 调用
   **且** 产出区无终止标志」三条同时成立时才判 —— 更保守，但仍有误报。
2. **TUI 的门禁弹出时机**：现在 agent 一停就弹。是否改为
   「阶段完成性判定通过后才弹」？这会改变交互，且用户可能希望保留
   「我就是要现在签」的权力。
3. **02 的 DAG 是否结构化落盘**：收益大（判据从文本变结构），
   成本也大（改 prompt + 工具契约 + 模板）。
