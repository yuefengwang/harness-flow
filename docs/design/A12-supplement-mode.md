## 1. 目标与定位

### 1.1 要解决的问题

上游 7.4 的四条返工路径（03 / 02 / 01 / 05）全部隐含同一个假设：
**「上游做错了，回去改」**。

但 04 阶段真正常见的发现是另一种：**「上游从没说过，我猜的」**。

这两件事的处置完全不同：

| 发现 | 正确处置 |
|---|---|
| 需求判断错了 | 推翻已有决策，重新决定 |
| **需求从未定义** | **保留已有决策，只补缺失的那部分** |

现在只有前者有出口（返工 01 = 重来）。后者在整套设计里是**死路**：

- A7 的 `spec_backed: inferred` 反例（攻击者无 spec 依据、自行推断期望值）
  按 A9 的 3.2 **不触发返工** —— 被丢掉。
- A8 的 `unverifiable` 意见（校验不了）**仅作提示** —— 被丢掉。
- A3 的 2.7 实测 `spec.md` 三段里两段常空
  （T1 的 `decisions` 五阶段全空、ADR 段全是 `___` 占位符）—— 无人处置。

这些信号是同一类：**审查者察觉到了什么，但没有业务真理可依据。**
A9 的 3.8 已把它们收集进 `route.unresolved` 并留档。
**A12 负责给它们一个真正的出口。**

### 1.2 与「业务真理不可能凭空产生」的关系

这是整套设计里**唯一直面那个最初判断**的任务。

前十一份文档做的都是「让 AI 的自述变成可核对的事实」——
它们提升的是**代码内部一致性**的审查能力。
A11 的 U11-1 已诚实声明：需求理解错误类缺陷**注入不出来**，
因为它不在代码里，在代码与意图的差里。

A12 不试图凭空产生业务真理。它做的是**把「缺哪一块真理」这件事精确定位，
然后向唯一的真理来源（用户）提问**。

> 判据：`supplement` 不产生任何新的业务判断。
> 它只把 `unresolved` 里的条目转成具体的问题，交给用户回答。
> **用户不回答，它就必须如实报告「仍未定义」，而不是让 AI 自行填补。**

### 1.3 本任务的范围

| 在范围内 | 不在范围内 |
|---|---|
| `intent=supplement` 时 01 阶段的行为差异 | `route.intent` 的产出与仲裁（**A9**） |
| 已有决策与 Gate 的保留策略（3.2） | 自动触发阈值（**A9 的 3.8**：第一批只留档） |
| `unresolved` 转成具体问题的呈现（3.3） | `unresolved` 的采集（**A9**） |
| 「无人应答」的诚实兜底（3.5） | 强制用户回答（做不到，也不该做） |
| TUI 的 D1/D2 选项区分 | 新增工作流阶段（2.1：代价过高） |

### 1.4 边界声明（必须诚实）

**`supplement` 无法保证信息真的被补上。**

三个具体的无能之处：

1. **用户可能不回答**。A3 的 2.7 已实测这个场景：T1 那次 agent 确实调用了
   `question` 工具（`01-brainstorming.md` 的 AI Output 段可见两次 `🔧 question`），
   但**无人应答**，`decisions` 一条都没落盘。
   `supplement` 走一圈回来，spec 依然是空的，只是多耗一轮。
2. **它依赖 `unresolved` 的质量**。若攻击者产出的 `inferred` 反例本身是胡说，
   `supplement` 会拿一个假问题去打扰用户 —— 而这会消耗用户对整套机制的信任。
3. **「补充」与「推翻」的界限由用户判断，不由程序**。
   D1/D2 的选择权在用户手上；仲裁器只在有充分证据时才建议（而第一批不自动触发）。

## 2. 现状：已实测的事实

本节实测均在临时任务（`pytest-a12-probe*`）上完成，**已清理**。

### 2.1 ⚠️ 不能真的新增一个阶段（代价核算）

最直觉的方案是在 `STAGES` 里插一个 `01b-supplement`。**实测代价过高**：

| 耦合点 | 实测数量 |
|---|---|
| `STAGES[idx]` 形式的索引访问 | **18 处**（`tui.py`、`service.py`、`commands.py`、`runtime.py`、`builder.py`、`pty.py`、`mock.py`、`state.py`、`web/routes/console.py`） |
| `len(STAGES) - 1` 的终点判断 | **5 处** |
| 按 `NN-name` 命名的模板与 hooks | 各 5 份 + 5 个 `check_*.sh` |
| 硬编码的五元 `STAGES` 副本 | `tests/e2e-flow/driver.py:54`、`tests/e2e-flow/verify.py:21` |

插入阶段会让 `stage_idx` 语义整体错位，**存量任务的 `.state` 全部失效**
（`stage_idx: 3` 从「评审」变成别的阶段）。

**定案**：`supplement` 是 01 的一个**模式**，不是新阶段。
Route 目标仍是 `01-brainstorming`，靠 `route.intent` 区分语义。

### 2.2 ✅ 返工到 01 不会清空已有产出（好消息）

实测：01 已有真实 ADR 内容时返工到 01。

```
=== 01-brainstorming.md 返工后内容 ===
> 🔄 **返工上下文（来自 04-Review）**
| # | 问题 | 严重程度 | 归属阶段 | 具体位置/描述 |
| 1 | token 过期语义未定义 | high | brainstorming | src/auth.py |
> 请优先修复上述问题。

# 01-Brainstorming

## Design Decision (ADR)
- **Proposal**: 用 JWT 做鉴权          ← 保留
- **Why this**: 无状态                  ← 保留
```

`inject_reroute_context` 把证据表注入到**文件顶部**，原内容完整保留。
这让 `supplement` 的「保留已有决策」有了现成的地基 —— **不需要新机制**。

### 2.3 ⚠️ 但 Gate 会被清空，而 `decisions` 存活

实测同一次返工前后：

| 状态 | 返工前 | 返工后 |
|---|---|---|
| `decisions`（用户拍板记录） | `{'用什么鉴权方案？': {'answer': 'JWT', 'decided_by': 'user'}}` | **完整保留** |
| `Gate.signed` | `True` | **`False`** |
| `Gate.items` | 全部 `checked` | 全部 `unchecked` |

清空 Gate 来自 `runtime.py:121` 的 `ss.reset_gate(name, next_stage)`，
注释写明理由：「带着上一轮的签名会让它直接放行」。

**这个区别正是 A12 的技术支点**：

- `decisions` 存活 → 「已拍板的决策」天然被保留，符合 `supplement` 语义。
- Gate 被清空 → 用户必须重新签署，这对两种 intent **都是正确的**
  （补充完信息也需要用户确认）。

**定案**：`supplement` **不需要改动 Gate 重置逻辑**。
沿用现有行为即可。这一条推翻了我起初的设想
（原以为 `supplement` 需要保留 Gate 签名）——
实测表明保留 Gate 反而错：补充信息后用户理应再确认一次。

### 2.4 ⚠️ 返工到 01 的 agent 拿不到任何下游上下文

`sw_lib/prompts/builder.py:116` 的 `_read_previous_stage`：

```python
def _read_previous_stage(self, task_name: str, stage_idx: int) -> Optional[str]:
    if stage_idx == 0:
        return None                      # ← 01 永远走这条
    prev_stage = STAGES[stage_idx - 1]
```

01 是 `stage_idx == 0`，所以**没有「前一阶段产出」可读**。

这在正向流程里是对的（01 本来就是起点），
但在**返工到 01** 的场景下是个真实缺口：analyst 不知道
下游发生了什么、为什么被打回来。

它唯一能看到的是 `inject_reroute_context` 注入到
`01-brainstorming.md` 顶部的证据表（2.2）——
而那份表在 A9 的 3.5 之后才有真实内容。

**定案**：`supplement` 模式必须显式注入「为什么回到这里」的上下文（3.3）。
不改 `_read_previous_stage`（那会影响正向流程），
而是在返工上下文块里补足。

### 2.5 `analyst` 角色已有 `ask_user` 工具（可直接用）

实测 `config/config.yaml` 的 `analyst` 角色：

```yaml
analyst:
  agent: opencode
  model: opencode/mimo-v2.5-free
  tools: [list_files, read_file, write_file, ask_user]
```

`ask_user` 已在工具集里 —— `supplement` 的提问能力**不需要新增工具**。

> ⚠️ 但 A3 的 2.7 实测：有 `ask_user` 不等于会被回答。
> T1 那次调用了两次 `question` 工具，`decisions` 仍全空。
> 这是 3.5 那条兜底存在的理由。

## 3. 设计

### 3.1 两种 intent 的行为差异表

| 维度 | `intent=revise`（既有语义） | `intent=supplement`（新增） |
|---|---|---|
| Route 目标 | `01-brainstorming` | `01-brainstorming`（相同） |
| 已有 ADR / 产出 | 可推翻重写 | **保留，只允许追加** |
| `decisions` 拍板记录 | 可推翻 | **保留**（2.3 实测天然如此） |
| Gate | 重置（2.3） | 重置（**相同** —— 2.3 的定案） |
| 注入的上下文 | 「以下判断有误，请重新决定」 | **「以下 N 个点在 spec 中无依据，请仅就这些点补充」** |
| agent 的任务 | 重新走歧义分析 | **只回答 `unresolved` 里的问题** |
| 准出要求 | 常规 Gate | 常规 Gate + **`unresolved` 逐条有明确状态**（3.4） |

> 核心差异只有两处：**注入的上下文**与**准出要求**。
> 其余全部沿用现有机制 —— 这是 2.2 / 2.3 实测带来的简化。

### 3.2 `hook-01-06: Supplement Scope`（新增）

> ⚠️ 编号实测：`hooks/01-brainstorming.md` 现有 **5 条** hook，
> `hook-01-05` **已被占用**（`Design Approval Gate`，第 24 行）。
> 新增 hook 的编号是 **`hook-01-06`** —— 起初写成 `01-05` 会与既有规则冲突，
> 且那条正是「推进需显式批准」，语义上极易混淆。

在 `hooks/01-brainstorming.md` 末尾新增：

```markdown
## hook-01-06: Supplement Scope (补充模式边界)
- **When**: 仅当返工 intent 为 supplement 时
- **Rule**: 只允许**追加**缺失的需求信息，**禁止推翻**已有的 ADR 与拍板决策。
  已有决策若确实需要改变，须由用户显式发起 revise，而非在补充中顺手改掉。
- **Check**: 已有 ADR 段落与 `.state` 的 decisions 条目在本轮后仍存在且未被改写
```

这条是**软约束（prompt 层）**，与 DEV-PROTOCOL 的定位一致。
硬约束在 3.4 的准出检查里。

### 3.3 注入的上下文形态

`supplement` 模式下，返工上下文块（2.2 的注入位置）改为：

```markdown
> 🔄 **需求信息补充请求（来自 04-Review）**
>
> 下游审查发现以下点**在需求与设计中找不到依据**，
> 实现时由 AI 自行推断。请就这些点做出明确决策。
>
> | # | 涉及模块 | 缺失的定义 | 来源 |
> |---|---|---|---|
> | 1 | src/auth.py | token 过期边界（exp == now 时是否有效）未定义 | 反例 ce-3（无 spec 依据） |
> | 2 | src/auth.py | 刷新 token 的失效策略未定义 | 设计意见 op-5（无法校验） |
>
> **请仅就上述点补充，不要推翻已有的设计决策。**
> 已有决策见下方 ADR 段落。
```

数据来源是 A9 的 `route.unresolved`（A9 的 3.8 已定字段结构）：

| 表列 | `unresolved` 字段 |
|---|---|
| 涉及模块 | `module` |
| 缺失的定义 | 反例的 `expected` 描述 / 意见的 `evidence.text` |
| 来源 | `source` + `id` + (`spec_backed` \| `status`) |

三条纪律：

1. **必须写明「由 AI 自行推断」**。用户需要知道这不是「AI 发现了 bug」，
   而是「AI 在这里猜了，猜得对不对你说」。
2. **不得把 `inferred` 反例描述成缺陷**。它是疑问，不是结论（A7 的 3.2）。
3. **必须附上已有决策的位置**，否则 agent 会重新走一遍歧义分析（2.4 的缺口）。

### 3.4 准出：`unresolved` 逐条必须有明确状态

`supplement` 轮次的准出检查（新增到 `hooks/check_01-brainstorming.sh`）：

每条 `unresolved` 必须落到三态之一，**不得二态化**
（DEV-PROTOCOL 第 3 节）：

| 状态 | 含义 | 判据 |
|---|---|---|
| `resolved` | 用户已拍板 | `.state` 的 `decisions` 新增了对应条目 |
| `deferred` | 用户明确表示「先不定，按现状走」 | `decisions` 中有显式的延后记录 |
| **`unanswered`** | **无人应答** | 既无拍板也无延后 → **进 3.5 的兜底** |

**`unanswered` 不算通过**（与 A6 的 3.3 `unavailable` 同构）。

### 3.5 「无人应答」的诚实兜底

这是本任务最重要的一节 —— 它决定 `supplement` 是有用还是变成空转。

A3 的 2.7 实测：agent 调了 `question` 但无人应答，`decisions` 全空。
若 `supplement` 遇到这种情况就静默放行，它就完全没有意义。

**定案**：连续两轮 `supplement` 后仍有 `unanswered` 条目时，
**中止自动流程**并向用户明确报告：

```
⚠️ 需求补充未获应答

审查发现 3 个未定义点，经两轮补充仍有 2 个无人应答：
  1. src/auth.py — token 过期边界（exp == now 时是否有效）
  2. src/auth.py — 刷新 token 的失效策略

继续推进意味着：这 2 个点将由 AI 自行推断，
其正确性不受任何机制保障，且不会再次提示。

请选择：[补充信息] / [确认按 AI 推断继续] / [中止任务]
```

三条纪律：

1. **让代价可见**，而不是静默兜底。用户有权选择「就按 AI 猜的走」——
   但必须是**知情的选择**。
2. **计入 `reroute_count`**（A9 的 3.6）。`supplement` 也是返工，
   同样受 `MAX_REROUTE` 约束，防止无限循环。
3. 「确认按 AI 推断继续」的选择须**落盘进 `decisions`**
   （`answer: "按 AI 推断继续"`），
   这样它会进入 A10 报告的「不确定」分类，而不是消失。

> 第 3 条是关键：用户放弃定义这件事**本身就是一条需要归档的决策**。
> A10 的 1.1 说「不确定的数量本身就是最有价值的指标」——
> 这类条目正是该指标的主要成分。

### 3.6 TUI 的 D1 / D2 选项

A9 的 2.6 已定案面板加 D 选项。本任务实现两者的文案与语义：

| 键 | 文案 | 写入 |
|---|---|---|
| A | 归档 | `target: 05-archive` |
| B | 返工到编码 | `target: 03-coding` |
| C | 返工到规划 | `target: 02-planning` |
| **D** | **补充需求信息（保留已有决策）** | `target: 01-brainstorming, intent: supplement` |
| **E** | **返工到需求层（推翻已有决策）** | `target: 01-brainstorming, intent: revise` |

> 顺序刻意把 `supplement` 放在 `revise` 前面：
> 前者是更常见、破坏性更小的动作。
> `revise` 会让用户已拍板的决策作废，应当更难被误按。

## 4. mock 模式

mock 下 `analyst` 产出固定文本，**不会真的调用 `ask_user`**。
因此 `supplement` 的核心行为（提问 → 用户回答 → 落盘 `decisions`）
在 mock 下不可验证。

分两层：

| 层 | 模式 | 目的 |
|---|---|---|
| 上下文注入、准出三态判定、兜底触发（3.3 / 3.4 / 3.5） | mock 即可 | 纯程序逻辑，可用夹具直接写 `decisions` 模拟用户应答 |
| 真实的提问质量（`unresolved` 是否被转成好问题） | **需真实 LLM** | 本批不做自动化验证，人工抽查 |

> 纪律：mock 下用夹具写入 `decisions` 是**允许的**（模拟用户应答），
> 但**必须同时有一个夹具不写入**，用来验证 3.5 的兜底会触发。
> 只测「有人应答」的路径等于没测这个任务的核心。

## 6. 实施顺序（内部）

1. `route.intent` 的读取与分支（依赖 A9 已产出该字段）。
2. `supplement` 上下文注入（3.3）—— 复用 `inject_reroute_context` 的注入位置（2.2）。
3. `hook-01-06` 规则文本（3.2，纯 prompt 层）。
4. 准出三态判定（3.4）。
5. **兜底与用户告知**（3.5）—— 本任务的核心，须在第 6 步之前完成。
6. TUI 的 D/E 选项（3.6）。

> 第 5 步先于第 6 步是刻意的：先把「无人应答怎么办」做对，
> 再开放入口。反过来会让用户能触发一个尚无兜底的流程 ——
> 那正是「静默空转」的温床。

## 7. 验收标准

**机制接通类**：

1. `intent=supplement` 时注入的是补充模式的上下文（3.3），
   `intent=revise` 时注入的是原有证据表。
2. 已有 ADR 段落在 `supplement` 轮次后**逐字保留**（2.2 已证实机制存在）。
3. `decisions` 在 `supplement` 轮次后完整保留（2.3 已证实）。
4. Gate 在两种 intent 下**行为一致**（都重置，2.3 的定案）。
5. D 键写入 `intent: supplement`，E 键写入 `intent: revise`。
6. 全部既有测试通过（**单调性**）。

**有效性类**（核心）：

7. **`unanswered` 不算通过**（3.4 的回归锚点）：
   `unresolved` 有条目而 `decisions` 无对应记录时，准出检查**失败**。

   若实现按二态处理（有 `decisions` 就算过 / 没有就跳过），此条必红。

8. **两轮无应答触发兜底**（3.5 的回归锚点）：
   连续两轮 `supplement` 且 `decisions` 无新增时，
   流程中止并产出含**具体条目列表**的告知（不是笼统一句「信息不足」）。

9. **「按 AI 推断继续」落盘**（3.5 第 3 条）：
   用户选择继续后，`decisions` 中有该记录，
   且 A10 报告的「不确定」分类包含这些条目。

   若只是放行而不落盘，此条必红 —— 那意味着用户的知情放弃**消失了**，
   事后无法复盘。

10. **`supplement` 计入 `reroute_count`**：
    三轮 `supplement` 后触达 `MAX_REROUTE`（依赖 A9 的 3.6）。

11. **不推翻已有决策**（3.2）：
    构造一个 `supplement` 轮次，agent 产出试图改写已有 ADR，
    准出检查应**检出并拒绝**。

12. **上下文含「由 AI 自行推断」的措辞**（3.3 第 1 条）：
    注入文本中明确区分「疑问」与「缺陷」，
    不把 `inferred` 反例描述成已确认的问题。

> 第 7、8、9 条是核心。
> 它们共同保证 `supplement` 不会退化成「走一圈什么都没变」——
> 而那是本任务最可能的失败形态。

## 8. 风险与遗留

| # | 风险 | 处置 |
|---|---|---|
| R1 | 用户被低质量问题打扰，失去信任（1.4 第 2 条） | 第一批**只能手选触发**（A9 的 3.8 不设自动阈值）。用户主动按 D 才进入，不会被 AI 自作主张打扰 |
| R2 | `supplement` 走一圈什么都没补，纯耗轮次 | 3.5 的兜底 + 计入 `reroute_count`。**验收 8 专门覆盖** |
| R3 | agent 在 `supplement` 中顺手改掉已有决策 | `hook-01-06` 软约束 + 准出硬检查（验收 11）。软硬双层，因为 prompt 约束不可靠 |
| R4 | `unresolved` 为空时用户仍按了 D 键 | 无条目时提示「当前无未定义点」并拒绝进入该模式，避免空转一轮 |
| R5 | 01 的 agent 拿不到下游上下文（2.4） | 由 3.3 的注入补足。**不改 `_read_previous_stage`** —— 那会影响正向流程的起点语义 |
| R6 | `intent` 字段被篡改可绕过 supplement 约束 | `intent` 在 A9 的顶层 `route` 键内，已纳入 HMAC 签名（A9 的 2.2 / 3.4） |

**明确遗留、不假装解决的问题**：

- **U12-1**：**无法强制用户回答**（1.4 第 1 条）。
  3.5 只能让代价可见，不能产生答案。
  A3 的 2.7 实测的「调了 `question` 但无人应答」是真实且常见的场景。
- **U12-2**：`unresolved` 的质量取决于 A7/A8，A12 无法过滤胡说的条目。
  低质量条目会浪费用户注意力，而注意力是最稀缺的资源。
- **U12-3**：`supplement` 只覆盖「AI 察觉到自己在猜」的情形。
  **AI 猜了但没察觉的地方，依然是盲区** ——
  这与 A11 的 U11-1 是同一个局限的两面。
- **U12-4**：自动触发阈值未定（A9 的 3.8 定案第一批不设）。
  当前完全依赖用户手选，意味着**用户不按 D 键，这套机制就永不启用**。
  这是刻意的保守，但也意味着它的实际价值待观测。
- **U12-5**：两轮的阈值（3.5）是拍的。与 A9 的 3.8 同一原则：先收集数据。

## 9. 本任务的红绿要点

### 9.1 自指风险

A12 的自指风险与其他任务不同：**它不产生判断，所以自指较轻**。
但有一处需要注意。

`unresolved` 条目转成「问题」的过程，若由 LLM 改写措辞，
就存在「AI 决定怎么问」的空间 —— 而问法会影响用户的回答。
极端情况：AI 把自己的推断写成引导性问题
（「token 过期边界应该是 `exp <= now` 对吧？」），
用户顺手确认，于是 **AI 的猜测经用户之手变成了「业务真理」**。

那比不问更糟：它给猜测盖上了权威的章。

**纪律**：`unresolved` 转问题必须是**模板化的机械拼装**（3.3 的表），
**不经 LLM 改写**。措辞固定为「X 未定义，请决策」，
**不得包含建议答案**。验收 12 覆盖这条。

### 9.2 环境自伤风险

1. 测试会反复写 `.state` 的 `decisions` 与 `route`。
   须用 `pytest-*` 前缀的临时任务并在 teardown 清理。
   **`workspace/tasks/` 下的用户任务一律不得触碰**。
2. `supplement` 会修改 `01-brainstorming.md`。
   测试须确认改的是临时任务的文件。
3. 撰写本文档的实测（2.2 / 2.3）已在临时任务上完成并清理，
   未触碰任何用户任务。

### 9.3 红的正确形态

| 验收项 | 红的正确形态 | 假绿风险 |
|---|---|---|
| **7 `unanswered` 不算通过** | 按二态实现（有 `decisions` 就过）时，构造「有 `unresolved` 无应答」应判失败，为红 | 夹具里 `unresolved` 为空 —— 那本来就该过，测不出三态。**夹具必须有条目且无应答** |
| **8 两轮触发兜底** | 无兜底时第二轮照常放行，断言「中止」为红 | 只测一轮。**必须真实跑两轮**，且第二轮的 `decisions` 确实无新增 |
| **9 知情放弃落盘** | 只放行不落盘时，断言 `decisions` 含该记录为红 | 断言「流程继续了」而不查 `decisions` —— 那样「静默放行」也绿，用户的选择消失无踪 |
| **11 不推翻已有决策** | 无准出检查时，改写 ADR 能通过，为红 | 用「agent 没改」的样本测 —— 那当然过。**必须构造一个真的改写了 ADR 的样本** |
| **12 措辞不含建议答案** | 若实现让 LLM 改写措辞，注入文本可能含引导性问法，为红 | 只断言「文本非空」或「含模块名」。**应断言不含建议答案的句式**，并断言转换过程零 LLM 调用（9.1） |
| **2 ADR 逐字保留** | 若实现整段重写 `01-brainstorming.md`，为红 | 断言「文件仍含 ADR 标题」—— 标题在但内容被清空也能过。**必须逐字比较原 ADR 段落** |
| **4 Gate 行为一致** | 若实现刻意为 `supplement` 保留 Gate 签名，断言「已重置」为红 | 这一条的方向容易搞反：2.3 实测表明**保留 Gate 才是错的**。补充完信息后用户理应再确认一次 |

### 9.4 特别提醒：第 12 条与 9.1 的自指

写 3.3 的注入逻辑时，最容易「顺手优化」的动作是让 LLM 把
`unresolved` 的技术描述改写成更自然的问句。**这个优化必须被拒绝。**

一旦 LLM 参与措辞，它就有机会把自己的推断写成引导性问题，
用户点头即等于给 AI 的猜测盖章 ——
**那是本套设计从第一份文档起就在防的东西，在最后一份文档里以最柔和的形式重现。**

纪律：转换过程用**字符串模板**，可用调用计数器断言零 LLM 调用。

### 9.5 单调性

本任务是**纯新增路径**：不选 D 键则完全不触发，既有流程零影响。

唯一的例外是 `hook-01-06` 会进入 01 的 prompt ——
它对 `intent=revise` 与正向流程**必须无效**，
否则正常的 01 阶段会被「禁止推翻已有决策」误伤（那是 revise 的合法动作）。
须显式测试：正向流程的 01 阶段 prompt **不含**该 hook 的约束文本。
