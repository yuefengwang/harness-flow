> ⏰ **时序：波 0。必须在 A6 / A7 / A8 / A9 实施之前执行。**

## 1. 目标与定位

### 1.1 为什么这件事必须单独成篇

它原本是 A11 的 3.6 与实施顺序第 1 步。拆出来的理由是**时序自相矛盾**：

| 职责 | 正确时序 |
|---|---|
| 基线采集（本任务） | 改造**之前** —— 数据一旦被覆盖就永久丢失 |
| 探针本体与对照实验（A11） | 改造**之后** —— 要观测的是改造后的行为 |

两者塞进同一份文档时，编号必然撒谎：
放在波 4 则那个不可逆的采集步骤会被漏掉；
提到波 0 则文档里大部分内容不该那么早做。

**拆开后每份只有一个时序位置。**

### 1.2 本任务的全部价值在于「抢救一次观测」

A4 的 U4-3 与 A9 的 U9-1 都把最终证明推给了 A11：

- U4-3：「provider 校验是廉价代理指标，不是真正的独立性证明。
  真正的证明只能来自 A11 的变异探针。」
- U9-1：「三轨全沉默与确实没问题不可分…
  真正的解法是 A11 —— 注入已知缺陷后若仍走优先级 6，说明整套审查是空转。」

而 A11 的对照实验需要两端：改造前与改造后。
**改造后那端随时可采，改造前那端只有现在。**

> 一句话：**本任务不建任何机制，只抢救一次再也不会有的观测机会。**
> 它的产出是一个 JSON 文件，但那个文件无法重新生成。

### 1.3 边界声明（必须诚实）

**基线已经不纯了。** 这一点必须写在最前面，不能等到风险章节。

实测当前仓库状态（`git log` HEAD = `5bf083b` "State integrity optimization"）：

| 任务 | 实施状态 | 对基线的影响 |
|---|---|---|
| **A0**（`.state` 完整性 + 签名） | ✅ **已实施** | `evidence.py` 存在，`state.py:229` 已调 `attach_signature` |
| **A1**（任务级 git 仓库） | ✅ **已实施** | `git_repo.py` 存在 |
| A2 / A3 / A5 | ❌ 未实施 | 无影响 |
| **A6**（客观轨） | ❌ 未实施 | `objective_check.py` 不存在 |
| **A7**（攻击者） | ❌ 未实施 | `counterexample.py` 不存在 |
| **A8**（设计审视者） | ❌ 未实施 | `design_review.py` 不存在 |
| **A9**（仲裁器） | ❌ 未实施 | `arbiter.py` 不存在 |

**结论**：严格意义上的「改造前」应是 A0 实施之前，那个时点**已经错过**。

但**审查侧完全未被改造** —— 04-review 仍是单 `reviewer` 角色
（实测 `config.yaml:86` 的 `stage_roles.04-review: reviewer`），
客观轨、攻击者、设计审视者、仲裁器四者一个都不存在。

而基线要观测的恰恰是**审查能力**。因此：

> **定案**：当前时点采集的基线对「审查能力」这个观测量**仍然有效**，
> 但 `harness_git_sha` 必须如实记录 `5bf083b`，
> 并在归档里显式标注 `baseline_purity: "review_side_clean"`
> ——「审查侧干净，地基侧已改造」。
>
> **不得**把它标成完整的改造前基线。A11 引用这份数据时，
> 结论只能表述为「审查侧改造带来的提升」，
> 不能表述为「全套设计带来的提升」。

三个具体的无能之处：

1. **A0 / A1 的影响无法剥离**。它们已经改变了 `.state` 结构与 git 布局，
   无法回退观测（回退会破坏你已有的任务数据）。
2. **样本量必然小**。真实 LLM 对照实验成本高，第一批可能只有个位数样本。
   **禁止用个例宣布结论**（承 A11 的 U11-5）。
3. **对照组的「无反应」可能有别的原因**。reviewer 没发现缺陷，
   也可能是那一次 LLM 采样恰好走偏，而不是机制无能。
   缓解靠多次重复（3.4），但无法根除。

| 特征 | 实测值 |
|---|---|
| `stage_roles.04-review` | `reviewer`（**单角色**，无并行轨） |

## 3. 设计

### 3.1 采集流程（全程只读被测代码，除变异注入外）

```
1. 前置检查：确认 A6-A9 未实施（2.1）；记录污染维度
2. 记录环境指纹：git sha + dirty 状态 + config 快照（3.2）
3. 选取变异样本：复用 A11 的算子定义（3.3）
4. 逐个样本：
      注入变异 → 跑现有测试判存活 → 存活者进入观测
      → 走一次完整 04-review（真实 LLM）
      → 记录 reviewer 的反应与最终 Route
      → revert 变异
5. 落盘归档（3.2），标记 read_only
```

### 3.2 归档格式

```jsonc
// workspace/probe/baseline-<date>.json   —— 一次性产物，只读
{
  "captured_at": "2026-08-23T…",
  "baseline_purity": "review_side_clean",   // 见 1.3 的定案
  "purity_detail": {
    "implemented_before_capture": ["A0", "A1"],
    "review_side_untouched": ["A6", "A7", "A8", "A9"],
    "note": "严格的改造前基线应在 A0 之前，该时点已错过。本基线仅对『审查能力』这一观测量有效。"
  },
  "env": {
    "git_sha": "5bf083b7a742ea3ff8341d559d965f9febfe73a3",
    "git_dirty": true,                      // 2.3 实测
    "git_status_summary": "M config/config.yaml; M hooks/check_05-archive.sh; M sw_lib/core/service.py",
    "mode": "real",                         // 必须 real；mock 无意义（A11 第 4 节）
    "config_snapshot": { /* 五角色全 opencode/mimo-v2.5-free */ },
    "review_stage_roles": {"04-review": "reviewer"}
  },
  "samples": [
    {"id": "M2-1", "file": "src/auth.py", "operator": "M2",
     "surviving": true,                     // 现有测试未捕获
     "runs": 3,                             // 重复次数（3.4）
     "route_targets": ["05-archive", "05-archive", "05-archive"],
     "reviewer_mentioned_defect": false,    // 人工标注（3.5）
     "counterexamples": 0, "opinions": 0}
  ],
  "detection_rate": 0.0,
  "sample_count": 1,
  "read_only": true
}
```

三条纪律：

1. **`detection_rate` 为 0 是预期结果**，不是失败（9.3 有专门提醒）。
2. **`mode` 必须是 `real`**。mock 下 reviewer 产出固定文本，
   对任何变异给同样输出，采到的是夹具而非能力（A11 第 4 节）。
3. **`read_only: true` 且文件权限设为只读**。它不可重新生成，
   任何后续写入都是破坏。

### 3.3 与 A11 的接口：复用算子，不重复定义

本任务**不定义变异算子**，直接用 A11 的 3.1：

| 算子 | 用途 | 是否用于基线 |
|---|---|---|
| M1（函数体换 `raise NotImplementedError`） | 被捕获变异 | ❌ **不用** —— A11 的 2.1 实测它会被现有测试抓住，测的是测试套件而非 reviewer |
| **M2（比较运算符边界偏移）** | 存活变异 | ✅ **主力样本**（A11 的 2.2 实测存活） |
| **M3（五层真嵌套）** | 存活变异 | ✅ 用于观测「结构缺陷是否被提及」 |
| **M4（布尔取反）** | 存活变异 | ✅ |
| M5-M8 | — | 第二批，视时间而定 |

> **实施依赖**：本任务需要 A11 的注入器（`injector.py`）。
> 若 A11 尚未开工，**本任务须先实现注入器的最小子集**
> （`find_sites` / `inject` / `revert` 三个函数 + M2 一个算子），
> 由 A11 后续扩充。
>
> ⚠️ 注入器必须遵守 A11 的 2.3 定案：
> **AST 定位 + 文本级精准替换，不用 `ast.unparse`** ——
> 后者会把单字符变异放大成 3 增 4 删并删掉注释，
> 基线数据会变成「reviewer 能否在噪音里发现缺陷」。

### 3.4 重复采样：对抗 LLM 随机性

每个样本跑 **N 次（默认 3）**，记录每次的 Route。

判定：

| 情况 | 记法 |
|---|---|
| 3 次全部 `05-archive` | 未检出（对照组的典型结果） |
| 3 次中有 1-2 次非 `05-archive` | **`unstable`** —— 单列，不计入检出也不计入未检出 |
| 3 次全部非 `05-archive` | 检出 |

`unstable` 这一态是刻意的：LLM 采样波动会让「偶然发现」看起来像能力。
**不得二态化**（DEV-PROTOCOL 第 3 节）。

### 3.5 人工标注：`reviewer_mentioned_defect`

对照组没有结构化产出（那是 A7/A8 才有的），
reviewer 的反应只体现在 `04-review.md` 的自然语言里。

**定案**：这一项**人工标注**，不做自动解析。

理由：自动解析 reviewer 的散文要么用正则（脆且会误判，
参见 A9 的 2.3 那个「反对归档被读成归档」的先例），
要么用 LLM 判断（那就引入了新的自问自答）。

> 基线的样本量很小（个位数），人工看几份 `04-review.md` 成本可接受。
> **宁可慢，不可用一个会误判的解析器污染唯一一份不可重采的数据。**

## 7. 验收标准

**机制接通类**：

1. 前置检查能正确识别 A6-A9 的实施状态，并在归档中标注污染维度。
2. `git_dirty` 与 `git_status_summary` 如实记录（2.3 实测当前为 dirty）。
3. 注入 → 判存活 → revert 全流程后，工作树**恢复到采集前状态**
   （逐字节比较被注入文件）。
4. 归档文件落盘后为只读，重复运行不覆盖已有基线（追加新文件）。
5. mock 下 `detection_rate` 为 `null` 而非 `0`。
6. 全部既有测试通过（**单调性**）。

**有效性类**：

7. **对照组的「未检出」被正确记录**：
   注入 M2 存活变异并走完 04-review 后，
   `route_target` 为 `05-archive`、`detection_rate` 为 `0.0`。

   > ⚠️ **这条的期望是「未检出」。** 断言方向极易写反（9.3）。

8. **M1 不进入基线样本**（A11 的 2.1）：
   算子集合中排除 M1，或若纳入则 `surviving: false` 且不计入分母。

9. **注入规模受控**（承 A11 的验收 7）：
   M2 的 diff 为 1 增 1 删，注释与 docstring 逐字保留。

10. **`unstable` 三态生效**（3.4）：
    构造一个 3 次结果不一致的样本（可用夹具模拟），
    记为 `unstable` 而非二态归类。

11. **基线不可重生成的保护有效**：
    尝试对同一日期重复采集时，不覆盖、不静默合并，而是报错或另建文件。

> 第 7 条是核心，且它是**全套设计里唯一一条「期望失败」的验收**。
> 第 11 条次之：它保护的是一份无法重做的数据。

## 9. 本任务的红绿要点

### 9.1 自指风险

本任务的自指风险**低于 A11**：它不评估任何机制，只做一次观测记录。

但有一处特殊风险：**采集脚本本身若有 bug，会把「探针没生效」记成「reviewer 没反应」。**

这与 A11 的 1.4 是同一类问题，但后果更重 ——
A11 的数据可以重采，**本任务的不能**。

纪律：采集前必须先用 A11 的 3.5 元测试验证注入器
（变异确实写入、diff 含变异、语法未坏、分类正确）。
**未经元测试的注入器不得用于基线采集。**

> 若 A11 尚未开工，元测试的最小子集须在本任务内先写 ——
> 这是第 2 步（注入器）与第 4 步（采集）之间不可省略的一环。

### 9.2 环境自伤风险（本任务最高之一）

1. **不得在 harness 自身注入变异**。实测 harness 工作树当前 dirty
   （`config.yaml`、`check_05-archive.sh`、`service.py` 处于 modified），
   `revert` 无法区分「探针的变异」与「用户未提交的改动」。
   被测对象须是 `repo/` 下或 `tmp_path` 的独立仓库。
2. **采集会走完整的 04-review 流程**，即会真实调用 LLM 并写 `.state`。
   须用专门的临时任务，**不得复用 `workspace/tasks/` 下的用户任务**
   （当前有 `T1`、`uw`、`uuuu`、`newtask` 等）。
3. 采集脚本的测试须全程 `tmp_path`。
   A0 实施期曾用真实路径探针截断 `workspace/tasks/T1/.state` ——
   本任务的破坏面更大（既改源码又跑流程）。

### 9.3 红的正确形态

| 验收项 | 红的正确形态 | 假绿风险 |
|---|---|---|
| **7 对照组未检出** | **期望值是 `05-archive` 与 `0.0`** | **断言方向极易写反**：直觉会写「注入缺陷应被检出」，于是断言 `03-coding`。那条断言在对照组必然失败，实施者会以为采集脚本有 bug 而去「修」它，**最终把基线采成一个假的高分**，A11 的对比彻底失去意义。见 9.4 |
| 3 工作树恢复 | 若 `revert` 用反向 patch 而非恢复备份，二次执行会把变异改回去，为红 | 只断言「文件已改变过」，不逐字节比对恢复结果 |
| 5 mock 下为 null | 实现若把 mock 也写 `0.0`，断言 `is None` 为红 | 断言 `not detection_rate` —— `0.0` 也满足，两者混为一谈，而这正是本任务最需要区分的一对 |
| 9 注入规模 | 用 `ast.unparse` 时为 3 增 4 删，断言 (1,1) 为红 | 只断言 diff 非空（承 A11 的 9.3 同名陷阱） |
| 10 `unstable` 三态 | 二态实现会把 2/3 次归入某一侧，断言 `unstable` 为红 | 夹具三次结果一致 —— 那测不出三态 |
| 11 不可覆盖 | 实现若直接 `write_text` 会静默覆盖，断言报错为红 | 断言「文件存在」—— 覆盖后它也存在。**须比对内容或 mtime** |

### 9.4 特别提醒：整份文档最容易犯的错

基线采集的正确结果是**「什么都没检出」**。

```python
# 对照组：注入存活变异后，改造前的 reviewer 应当毫无反应
assert sample["route_targets"] == ["05-archive"] * 3   # 缺陷被放过 = 基线正确
assert baseline["detection_rate"] == 0.0               # 0 是预期值
```

写这段代码时，每一条直觉都在喊「这不对，缺陷应该被发现」。
于是最可能发生的事情是：实施者认为采集脚本坏了，
去调整注入方式、调整判定条件、甚至调整 prompt，
直到「基线也能检出缺陷」——
**那一刻，这份不可重采的数据就被永久毁掉了**，
而且毁掉的方式是「看起来变好了」。

**采集脚本的注释里必须用醒目的方式写明：这里期望的是未检出。
`detection_rate == 0.0` 是成功，不是失败。**

> 这正是 A11 的 9.4 那条提醒的加强版 ——
> 在 A11 里写错还能重跑，在这里写错就没有第二次。

### 9.5 单调性

本任务**不改变任何生产行为**，纯新增采集脚本与归档目录。

唯一的单调性风险是注入残留（9.2 第 1 条）：
若变异未 revert 会污染被测仓库，表现为「莫名其妙的测试失败」。

> **回滚本任务等于放弃证明整套设计有效。**
>
> 与其他任务不同，这里的「回滚」不是恢复到某个可工作状态,
> 而是**永久失去一个时间窗口**。A4 的 U4-3 与 A9 的 U9-1 会永远悬空：
> 机制会继续运行、测试会继续绿，但「审查能力是否真的提升」
> 这个问题将没有答案 —— 而那正是整个 `harness-flow` 自校验命题的核心。
>
> 因此本任务**可以做得粗糙，但不能不做**。
> 三个样本的基线远好过零个。**宁可采得少，不可采得晚。**
