# 设计文档索引：自校验能力建设

> 版本：2026-08-23
> 拆分原则：**一份文档 = 一个可独立交付的开发任务 = 一个 agent 能独立完成的范围**。
> 每份文档自带前置依赖、验收标准、回滚方式，可单独派发。
>
> 🔒 **全部任务的实施均须遵守** [`DEV-PROTOCOL.md`](DEV-PROTOCOL.md)：
> 以软约束形式手动执行红绿准出范式。harness-flow 自身的硬机制（A2 的 `red_witness`）
> 尚未建成，但**不能用一个未经自校验的实现去构建自校验机制**。
> 每份任务文档末尾均有「本任务的红绿要点」，列出该任务特有的假绿风险。
>
> 🔀 **多 agent 并行派发见** [`PARALLEL.md`](PARALLEL.md)：
> 本文档第 4 节的波次表是**依赖顺序**的权威，但依赖不冲突 ≠ 文件不冲突。
> PARALLEL.md 补的是文件足迹矩阵与「单一写者」分组，以及派发工具 `scripts/wave.sh`。
> 它同时含一份**按代码实测的状态审计** —— 本清单的 ✅ 只表示设计文档写完，不表示已实现。

## 1. 为什么拆

`docs/design-reviewer-independence.md`（v2，585 行）已包含 13 个任务、
跨越配置层 / 图编排 / prompt 组装 / hook 脚本 / 状态存储五个层面。
作为单个开发任务过大：改动面广、回滚粒度粗、无法并行推进。

拆分后每份文档聚焦一个**单一职责的可交付单元**。

**波 0 加四波**，每波内部可并行。**本表是执行顺序的唯一权威**：

## 6. 全局验收

单个任务的验收见各自文档。**全局有效性判据只有一条**：

> A11 的变异注入探针在改造前后形成对照：
> 改造前 reviewer 对注入缺陷无反应，改造后攻击者产出可复现反例、
> 设计审视者报告结构缺陷。

> ⚠️ **这条判据由两个任务共同承担**：「改造前」那一端来自 **B0**（波 0），
> 「改造后」那一端来自 **A11**（波 4）。
> **缺 B0 则只剩一个绝对数字，证明不了「提升」** ——
> 此时 A11 须在报告中标 `comparison: unavailable`，
> 不得用改造后的绝对检出率冒充有效性证明。

其余任务的验收标准均属「机制接通」，不足以证明审查能力提升。

## 7. 撰写剩余文档时的要求

**全部十四份已完稿。** 以下要求已在每份中落实，保留作为后续新增文档的规范 ——
每份文档除本体设计外，**必须包含**：

1. 开头引用 [`DEV-PROTOCOL.md`](DEV-PROTOCOL.md)。
2. 末尾一节「本任务的红绿要点」，内容为一张表：
   每个验收项对应「红的正确形态」与「假绿风险」两列。

> 第 2 条不是形式要求。写这张表时会被迫回答
> 「这条验收标准怎么可能失败」—— 若答不出来，
> 说明该验收标准是空的，本身就该重写。

### 已知的自指风险（撰写时特别注意）

| 文档 | 自指风险 |
|---|---|
| **B0** | 自指本身轻（只观测、不评估），但**后果最重**：采集脚本若有 bug，会把「探针根本没生效」记成「reviewer 没反应」，两者在数据上完全同形。A11 的数据可以重采，**本任务的不能**。更险的是方向性错误 —— 基线的正确结果是 `detection_rate == 0.0`，而每一条直觉都在喊「缺陷应该被发现」，实施者极可能把采集脚本一路「修」到能检出，**那一刻数据以「看起来变好了」的方式被永久毁掉**。**已定案**：未经 A11 的 3.5 元测试验证的注入器不得用于基线采集；采集脚本注释须醒目写明「未检出即成功」（见 B0 的 9.1、9.4） |
| **A0** | 实现「证据不可伪造」。测试若绕过受控入口直接写 `.state`，就是在验证时使用被禁止的行为。**已定案**：绕过用于构造攻击样本是必要的，用于制造通过是禁止的（见 A0 的 9.1） |
| **A1** | 自指风险低，但有**环境自伤风险**：测试要反复 `git init` / `commit`，若误在 harness 仓库自身执行会污染用户 git 状态。已定案：全部走 `tmp_path`，且事后断言真实仓库状态未变（见 A1 的 9.1） |
| **A3** | 断言「事实包内容正确」需要期望值，若期望值由 `fact_pack` 自己生成即是自问自答的翻版。**已定案**：期望值手工写死，diff 断言必须用真实 git 仓库（mock 会按实现者的错误预期返回，恰好掩盖 2.1 那个头号缺陷），pytest 采集必须真跑（见 A3 的 9.1） |
| **A4** | 测试要反复改 `_manager.config` 这个**模块级全局单例**，一个用例不还原会污染其余全部用例（撰写本文档时的探针已实测到此现象）。**已定案**：`deepcopy` 快照还原嵌套 `RoleConfig`，并断言磁盘 `config.yaml` 未被改动（见 A4 的 9.1）。另有一条特殊纪律：验收 9 的兼容性快照**必须在改造前采集**，否则是自己和自己比对（9.3） |
| **A2** | 实现 `red_witness` 本身。其测试**必须**手动走完整红绿流程 —— 此时还没有机制可依赖 |
| **A6** | 实现「检测测试是否有效」。不得用无效测试验证它（详见 A6 第 9.1 节） |
| **A7** | 反例执行器的测试本身也是 pytest 测试，若不隔离会出现「测试执行器的测试」被执行器当成反例执行。更深一层：判据「退出码 1 = 反例成立」**假设了 pytest 的退出码语义**，该假设若错，三态判定连同它的测试会一起错且自证正确。**已定案**：三态映射须用真实 pytest 进程验证，期望值取自实测表（见 A7 的 9.1） |
| **A8** | 校验器为意见「打分」，而 `call_count` 若只统计 diff 内文件，会**为错误意见背书**（跨文件调用看不见）。**已定案**：全 `target_dir` 计数（见 A8 的 2.2、9.1） |
| **A9** | 仲裁器是**判据的判据**。其夹具的三轨输入格式定义在 A6/A7/A8 文档里 —— 照自己的理解造夹具，测的是「我的理解自洽」。**已定案**：夹具字段逐个对照上游文档抄写并注明出处；核心验收（11/12/13）都是「改造前必红」形态，**必须在改造前先跑一遍并记录失败输出**（见 A9 的 9.1） |
| **A11** | 实现变异探针。**两层自指，第二层无法自我消除**：① 探针自身若失效会静默放过一切 → 需「探针能检出已知缺陷」的元测试（A11 的 3.5）；② **变异算子编码了写文档者对「什么是缺陷」的理解，而 A7/A8 的 prompt 出自同一理解** —— 漏想的缺陷类型，探针不注入、reviewer 不寻找，而检出率会显示 100%。这是「判据与产出同源」在**元层面**的重现。**已定案**：算子取自变异测试领域的成熟算子集（ROR/LCR/AOR），报告显式声明该局限，且**检出率不作门禁** —— 一个自指的指标不该有生杀权（见 A11 的 9.1） |
| **A12** | 自指较轻（不产生判断），但有一处致命：`unresolved` 转成问题时若由 LLM 改写措辞，它可能把自己的推断写成**引导性问题**（「过期边界应该是 `exp <= now` 对吧？」），用户顺手确认 → **AI 的猜测经用户之手变成「业务真理」**，比不问更糟（给猜测盖了权威的章）。**已定案**：转换必须是机械的字符串模板拼装，不经 LLM，且不得包含建议答案（见 A12 的 9.1、9.4） |

> A2 与 A11 的自指最重。A2 是**唯一没有前置机制可依赖**的任务 ——
> 它的正确性完全依赖执行者手动遵守协议第 1 节。
>
> **B0 的自指最轻但代价最高** —— 它是唯一「错一次就没有第二次」的任务。
> 其余任务的自指风险靠迭代可以逐步收敛，B0 不行。
>
> **A11 是唯一明确承认自己无法自证的任务**（第二层自指）。
> 把这件事写出来，比造一个看起来严密的闭环更有价值 ——
> 因为一个自称已闭环的自校验系统，恰恰是最初那个问题最完整的形态。
