## 1. 目标与定位

### 1.1 要解决的问题

前十份文档建了一整套机制：事实包、异构模型、客观轨、反例、交叉校验、仲裁器。
每一份都有自己的验收标准，而那些标准**几乎全都在验证「接线正确」** ——
prompt 里有 diff、启动了两个 agent、退出码映射对、篡改能检出。

**没有一条能回答那个真正的问题：审查能力真的提升了吗？**

上游 9.4 把验收分成「机制接通类（必要但不充分）」与「有效性类（真正的判据）」，
并明确写着：「**不要用前六条宣布完成**」。A11 就是那个有效性类。

判据的形态是**对照实验**：

```
往代码里注入一个已知缺陷
    ├─ 改造前的 reviewer：无反应（对照组）
    └─ 改造后的三轨：攻击者产出可复现反例 / 设计审视者报结构缺陷 / 仲裁器路由到 03
```

> 一句话概括本任务：**它是唯一一个「失败了就说明前十份文档白做」的测试。**
> 其余任务的测试失败只说明该任务有 bug。

### 1.2 本任务的范围

| 在范围内 | 不在范围内 |
|---|---|
| 变异算子集合（可控、可复现、可撤销） | 变异算子的自动生成（需要更强的程序分析） |
| 注入器：精准文本替换，不破坏无关内容 | 生产流程常态化运行（本批只做离线实验） |
| 对照实验编排：改造前 / 改造后同缺陷对比 | 变异分数作为准出门禁（数据不足，见 U11-4） |
| 检出率报告与失败模式归属分析 | 跨任务的统计基线（需要样本积累） |
| **探针自身的元测试**（1.4） | 对非 Python 项目的变异（U11-3） |

### 1.3 边界声明（必须诚实）

**检出率高不等于审查有效，只等于「对这批变异有效」。**

四个具体的无能之处：

1. **变异是我们自己选的**。变异算子编码了我们对「什么是缺陷」的理解 ——
   而这个理解和写 reviewer prompt 的是同一批人（同一个我）。
   **这是本任务无法自我消除的自指**（9.1 第二层）。
2. **存活变异不等于有真 bug**。等价变异（语义未变的改动）会被算成漏检，
   人工确认成本高，且无法自动判定。
3. **注入的缺陷形态与真实 bug 分布不同**。真实缺陷里大量是
   需求理解错误 —— 那类东西**注入不出来**，因为它不在代码里，
   在代码与意图的差里。而意图恰恰是缺失的那一环（A3 的 2.7）。
4. **对照组只能跑一次**。改造前的状态一旦被改造覆盖，
   对照数据无法重采。因此**基线必须在改造前采集并落盘归档** ——
   该职责已拆出为 **B0**（见 3.6）。

> 第 3 条是全套设计最深的局限，A11 只能让它可见，无法解决它。
> 最初那个判断没有被推翻：**业务真理不可能凭空产生。**
> 变异探针能验证「代码内部一致性的审查能力」，
> 不能验证「代码是否符合用户真实意图」。

### 1.4 探针自身必须被验证（自指的正面处理）

README 已标注本任务的自指风险：
「探针自身若失效会静默放过一切；需一个『探针能检出已知缺陷』的元测试」。

具体的失效形态（3.5 有实测）：

| 失效形态 | 后果 |
|---|---|
| 变异根本没写进文件 | 三轨当然没反应，被记成「审查无效」—— **冤枉** |
| 变异写进去了但 diff 不含它 | 三轨看不到，同上 |
| 变异破坏了语法 | 反例全 `BROKEN`，被记成「审查无效」 |
| 变异被现有测试直接抓住 | 客观轨 `hard_fail`，仲裁器命中优先级 1 —— **看起来检出了，但那是测试的功劳，不是 reviewer 的** |

最后一行最危险：它会让探针**报告一个虚高的检出率**。3.2 有专门的处置。

## 2. 现状：已实测的事实

本节的实测在 `/tmp/a11probe` 的临时仓库完成，**已清理**。
实测直接改变了实现方案（2.2）。

### 2.1 ⚠️ 上游 9.4 第 7 条的变异会被现有测试直接抓住

上游验收 7 写：「将 diff 中某函数体替换为 `raise NotImplementedError`，
攻击者应产出可复现反例」。

实测（一个 `verify_token` 函数 + 两条现有测试）：

| 变异 | 现有测试结果 |
|---|---|
| 原始代码 | `2 passed` |
| **M1：函数体换成 `raise NotImplementedError`**（上游原文） | **`2 failed`** |

**M1 是一个「被现有测试抓住」的变异。** 它进不了攻击者的视野 ——
客观轨（A6 的 O2）在更前面就 `hard_fail`，A9 的仲裁器命中**优先级 1**
直接路由到 03-coding，攻击者的反例根本不影响结果。

用它做探针，测到的是「现有测试套件有效」，**不是「reviewer 有效」**。

**定案**：变异必须按「是否被现有测试捕获」分成两类，
**只有存活变异（surviving mutant）才是有效探针**：

| 类别 | 定义 | 用途 |
|---|---|---|
| **被捕获变异** | 注入后现有测试转红 | **不用于评估 reviewer** —— 只用于验证探针自身写入成功（1.4） |
| **存活变异** | 注入后现有测试仍全绿 | **唯一有效的探针**：测试没抓到，只能靠审查抓 |

这是本文档对上游 9.4 的一处实质修正。上游的 M1 属前者。

### 2.2 ⚠️ 存活变异实测可构造，且极其廉价

同一份代码，把 `<` 改成 `<=`（边界条件，现有测试未覆盖 `exp == now`）：

```python
-    if token["exp"] < now:
+    if token["exp"] <= now:
```

实测结果：**`2 passed`** —— 现有测试完全没有察觉。

这正是有效探针的形态：一个真实的边界错误，测试放过了它，
**只有审查能抓住**。而且它只改一个字符，符合「最小变异」原则。

### 2.3 ⚠️ 头号实现陷阱：`ast.unparse` 会把单字符变异放大成整文件重写

最自然的注入实现是 AST 改写后 `ast.unparse` 回写。**实测这条路不可用。**

对一份含 docstring、注释、双引号的代码做同一个 `<` → `<=` 变异：

| 注入方式 | `git diff --numstat` | 副作用 |
|---|---|---|
| **AST + `ast.unparse` 整文件回写** | **`3	4`**（3 增 4 删） | 注释被删除、双引号变单引号、末尾换行丢失 |
| **AST 定位 + 文本级精准替换**（定案） | **`1	1`** | 无 |

`ast.unparse` 的实测输出证实注释确实消失：

```
输入:  # 这个阈值来自业务规格 SPEC-3
输出:  （该行不存在）    → "SPEC-3" in out == False
```

三个后果，每个都足以让探针失效：

1. **注释被删**。若被测代码靠注释表达意图，变异引入了大量无关差异 ——
   设计审视者会去评论那些噪音，而不是那个缺陷。
2. **diff 被噪音淹没**。A3 的事实包给 reviewer 的是 `diff.patch`。
   3 增 4 删里只有 1 行是真缺陷，其余是格式抖动。
   探针测的就不再是「能否发现缺陷」，而是「能否在噪音里发现缺陷」。
3. **`git diff` 规模失真**。A3 的 2.8 用 numstat 做风险排序，
   虚高的改动量会让排序错乱。

**定案**：注入器用 **AST 定位 + 文本级精准替换**。
AST 只用来找位置（`lineno` / `col_offset` / `end_col_offset`），
替换在原始文本的字节区间上做，**其余字节一律不动**。

实测该方案的 diff（`-U0`）：

```
@@ -6 +6 @@ def verify_token(token, now):
-    if token["exp"] < now:
+    if token["exp"] <= now:
```

干净的一行换一行，注释与引号全部保留。

### 2.4 嵌套深度探针可被 AST 量化（上游 9.4 第 8 条可行）

上游验收 8 要求「注入功能正确但嵌套深度 5 的变更，
设计审视者应报 `hook-03-03`，且 evidence 深度值能通过 AST 校验」。

实测构造一个五层嵌套的 `classify` 函数，用 A8 的 `nesting_depth` 同法计量：

```
AST 测得嵌套深度: 5
```

与 A8 的 3.2（`nesting_depth` 校验 `hook-03-03`，阈值来自
`hooks/03-coding.md:15` 的「Max 3 nested if-else」）对得上。
**该探针可行**，且期望值可由程序独立计算，不需人工标注。

> ⚠️ 但须注意 A8 的 2.4 已实测 `elif` 链会被误算为嵌套。
> 构造 M3 时**必须用真嵌套（缩进递增）而非 `elif` 链**，
> 否则测的是 A8 的那个 bug，不是它的能力。

### 2.5 A11 的观测量必须包含 A9 的路由结果

上游 9.4 的验收 7-9 只观测「攻击者是否产出反例」「设计审视者是否报规则」。
**不够** —— 三轨结论最终要汇成一个动作。

A9 的 U9-1 已把这件事推给本任务：
「三轨全沉默与确实没问题不可分…**真正的解法是 A11 的变异探针** ——
注入已知缺陷后若仍走优先级 6，说明整套审查是空转」。

**定案**：主要观测量是**仲裁后的 Route**，而非单轨反应：

| 观测量 | 期望（注入存活变异后） |
|---|---|
| **A9 的 `route.target`** | `03-coding`（**主判据**） |
| A9 的 `route.priority` | 2（反例）或 3（设计意见）；**不应是 1** |
| A7 的反例 | 至少一条 `CONFIRMED` 且 `spec_backed != inferred` |
| A8 的意见 | 命中对应 `rule` 且 `verification.status == verified` |
| A9 的 `arbitration` | 不应是 `no_valid_conclusion` |

`priority` 不应是 1 是个重要的细节：若为 1，说明客观轨抓住了它，
即这不是存活变异（2.1），探针样本选错了。

## 3. 设计

### 3.1 变异算子集合（第一批）

全部满足三条：**可控**（只改一处）、**可复现**（种子固定）、**可撤销**（原文备份）。

| id | 算子 | 形态 | 预期捕获轨 | 上游依据 |
|---|---|---|---|---|
| **M1** | 函数体替换为 `raise NotImplementedError` | 被捕获变异 | 客观轨（**不评估 reviewer**） | 9.4 第 7 条（**已修正定位**，2.1） |
| **M2** | 比较运算符边界偏移（`<`↔`<=`、`>`↔`>=`） | **存活** | A7 攻击者 | 本文档新增（2.2 实测） |
| **M3** | 注入五层真嵌套（功能等价） | **存活** | A8 设计审视者 | 9.4 第 8 条 |
| **M4** | 布尔取反（`and`↔`or`、去掉 `not`） | **存活** | A7 攻击者 | 本文档新增 |
| **M5** | 返回值常量替换（`True`→`False`、`None`→`0`） | 视覆盖率而定 | A7 攻击者 | 本文档新增 |
| **M6** | 引入单次使用的多余抽象（功能等价） | **存活** | A8（`call_count`） | 9.4 第 9 条的正向对照 |
| **M7** | 越界改动：在 `target_dir` 外改一个文件 | 被捕获 | 客观轨 O5 | 呼应 A6 的验收 5 |
| **M8** | **伪造 evidence**：提交声称「深度 6」而实际为 2 的意见 | — | A8 的交叉校验应**驳回** | 9.4 第 9 条 |

M8 是**反向探针**：它不注入代码缺陷，而是注入一个**假的审查结论**，
验证 A8 的交叉校验会驳回它、且不产生 Route 效果。
**这一条检验的是「审查者说了不算」，而非「审查者能发现问题」。**

> M1 与 M7 保留在集合里但**不计入检出率** —— 它们的用途是
> 验证探针写入成功（1.4 的第一、二种失效形态）。
> 它们必须让客观轨转红；**若连它们都不红，说明探针根本没生效**。

### 3.2 检出率的正确算法（避免虚高）

```
候选变异 = 全部注入成功的变异
存活变异 = 候选中「现有测试仍全绿」的子集        ← 唯一的评估分母
检出     = 存活变异中「A9 路由到 03-coding 且 priority != 1」的子集

检出率 = |检出| / |存活变异|
```

三条纪律：

1. **分母是存活变异，不是全部变异**。把 M1 计入会让检出率虚高（2.1）。
2. **`priority == 1` 的检出不算**。那是客观轨的功劳。
   若某个「存活变异」竟触发了 `priority == 1`，说明它其实被捕获了，
   应从分母中移出并记为样本分类错误。
3. **`arbitration != ok` 的情形单独统计**，不计入检出也不计入漏检 ——
   那是「审查未产生有效结论」（A9 的 N1），是第三种状态。
   **不得二态化**（DEV-PROTOCOL 第 3 节的三态汇报要求）。

### 3.3 注入器：`sw_lib/probe/injector.py`

```python
@dataclass
class MutationSite:
    file: Path
    lineno: int
    col_offset: int
    end_col_offset: int
    original: str          # 被替换的原始片段
    replacement: str

@dataclass
class InjectionResult:
    site: MutationSite
    applied: bool
    diff_numstat: Tuple[int, int]     # (增, 删)，须为 (1, 1) 或极小值
    syntax_ok: bool                   # 注入后能否 ast.parse
    captured_by_tests: bool           # 现有测试是否转红 → 决定分类（3.2）

def find_sites(path: Path, operator: str) -> List[MutationSite]:
    """AST 定位。只返回位置，不改内容。"""

def inject(site: MutationSite) -> InjectionResult:
    """文本级精准替换（2.3 的定案）。原文备份后写入。"""

def revert(site: MutationSite) -> None:
    """恢复原文。必须幂等。"""
```

四条实现纪律：

1. **不用 `ast.unparse` 回写**（2.3）。AST 只定位，替换在字节区间上做。
2. **注入后立即 `ast.parse` 自检**。语法坏了即 `syntax_ok: False`，
   该样本作废（1.4 第三种失效形态）。
3. **注入后立即量 `git diff --numstat`**。超过阈值（如增删各 > 2）即作废 ——
   那意味着替换范围失控。
4. **`revert` 必须幂等且在 `finally` 中调用**。探针跑一半崩了
   不能把变异留在用户代码里（9.2）。

### 3.4 对照实验编排：`sw_lib/probe/experiment.py`

### 3.5 探针自身的元测试：`tests/probe/test_probe_meta.py`

对应 1.4 的四种失效形态，每种一个用例：

| 元测试 | 断言 |
|---|---|
| 变异确实写入 | 注入后文件内容与原文不同，且 `git diff` 非空 |
| 变异出现在 diff 里 | `diff.patch`（A3 事实包）含该变异行 |
| 语法未被破坏 | 注入后 `ast.parse` 成功；故意造一个语法坏的变异应被判 `syntax_ok: False` |
| **分类正确** | M1 判 `captured_by_tests: True`；M2 判 `False` |
| **注入规模受控** | M2 的 `diff_numstat == (1, 1)`（2.3 的回归锚点） |
| `revert` 幂等 | 连续 revert 两次，文件内容等于原文 |

> 最后两条是本任务最容易被跳过的元测试，
> 而它们恰好对应实测发现的两个真实陷阱（2.3 与 3.3 的第 4 条）。

| `samples[].route_targets` | 对照组的路由结果，构成对比的一端 |

> 证明不了「提升」。此时须在报告中标
> `comparison: unavailable`，**不得用改造后的绝对检出率冒充有效性证明**。

## 4. mock 模式

**本任务在 mock 下不可能有意义。**

变异探针测的是**真实模型面对缺陷的反应**。
mock agent 产出的是夹具里写死的固定反例 —— 它对任何变异都给同样的输出。
在 mock 下跑探针，检出率完全由夹具决定，与审查能力无关。

因此分两层：

| 层 | 模式 | 目的 |
|---|---|---|
| **注入器与元测试**（3.3 / 3.5） | mock 即可，**不需 LLM** | 纯程序逻辑：定位、替换、分类、revert |
| **对照实验**（3.4） | **必须真实 LLM** | 这是本任务的目的所在 |

> 纪律：对照实验的结果**不得**在 mock 下产出并当成有效数据。
> 报告里必须记录 `mode: real` 与实际 provider/模型名；
> mock 下运行时报告须标 `mode: mock, detection_rate: null`
> —— **不是 0，是 null**，「未测量」与「测量为零」是两件事。

## 7. 验收标准

**机制接通类**：

1. `find_sites` 能在给定文件里定位全部目标算子的位置。
2. `inject` 后文件语法合法（`ast.parse` 成功）。
3. `revert` 幂等：连续两次后文件等于原文（逐字节比较）。
4. 探针崩溃时变异不残留（`finally` 中 revert，验收 13 有专门用例）。
5. 报告区分 `mode: real` 与 `mode: mock`，后者 `detection_rate` 为 `null`。
6. 全部既有测试通过（**单调性**）。

**有效性类**（本任务的全部意义所在）：

7. **注入规模受控**（2.3 的回归锚点）：
   M2 的 `diff_numstat == (1, 1)`，且注入后文件中的**注释与 docstring 逐字保留**。

   用 `ast.unparse` 实现时此条**必红** —— 实测为 `(3, 4)` 且注释消失。

8. **变异分类正确**（2.1 的回归锚点）：
   M1 判 `captured_by_tests: True`，M2 判 `False`。

   若不做分类（把两者一视同仁），检出率会虚高，此条必红。

9. **存活变异确实存活**：M2 注入后现有测试**全绿**（实测 `2 passed`）。
   若转红，说明样本选错，须换位点。

10. **改造前基线检出率可采集**：对照组对存活变异**无反应**，
    `route.target` 仍为 `05-archive`。

    这是**对照组的期望结果** —— 它「失败」才是正常的。
    这条断言的方向极易写反（9.3）。

11. **改造后检出率显著高于基线**：同一批存活变异，
    实验组的 `route.target == "03-coding"` 且 `priority != 1`。

    **这是全套设计的唯一有效性判据。**

12. **失败模式不重叠**（上游 9.4 第 10 条）：
    M2（边界错误）由 A7 攻击者捕获，M3/M6（结构问题）由 A8 设计审视者捕获。
    两者**不应互相替代** —— 若 M3 也主要由攻击者捕获，
    说明 A8 未产生独立价值。

13. **伪造 evidence 被驳回**（M8，上游 9.4 第 9 条）：
    声称「深度 6」实际为 2 的意见，`verification.status == refuted`，
    且**不产生 Route 效果**（`priority` 不为 3/4）。

14. **探针失效可自检**（1.4 的四种形态，3.5 的元测试全绿）：
    故意让注入不写入 / 语法坏 / diff 不含变异，探针应**报告样本作废**
    而非报告「审查无效」。

15. **N1 空转防护可复现**（上游 9.4 第 11 条）：
    构造「反例全部不可复现且无有效设计意见」的场景，
    仲裁器不走优先级 6（与 A9 的验收 16 呼应，此处从探针侧独立验证）。

> 第 7、8、10、11 条是核心。
> 7/8 保证探针自身可信，10/11 构成对照实验的两端。
> **没有 10，第 11 条只是一个绝对数字，证明不了「提升」。**

## 9. 本任务的红绿要点

### 9.1 自指风险（全套设计最重的两个之一）

**第一层**：探针验证「审查机制是否有效」，
而探针自身的有效性由谁验证？

处置是 3.5 的元测试，但它只能覆盖**机械失效**
（没写入、语法坏、diff 不含、分类错）。
**它无法验证「这批变异是否代表真实缺陷」** —— 那是第二层。

**第二层，无法自我消除**：
变异算子编码了我写这份文档时对「什么是缺陷」的理解，
而 A7/A8 的 prompt 也出自同一个理解。
**若我漏想了一类缺陷，探针不会注入它，reviewer 也不会去找它，
而检出率会显示 100%。**

这是「判据与产出出自同一隐状态」在**元层面**的重现 ——
正是本套设计一开始要解决的那个问题，在最后一份文档里又出现了一次。

**诚实的处置**（不假装解决）：

1. 算子取自变异测试领域的**成熟算子集**（ROR 关系算子替换、
   LCR 逻辑算子替换、AOR 算术算子替换），而非自创 ——
   借用外部的、与本项目无关的缺陷分类。
2. **在报告里显式声明这个局限**（U11-2），
   不把检出率当成「审查能力已验证」的证明。
3. 检出率**不作门禁**（U11-4）—— 一个自指的指标不该有生杀权。

> 这是全套十二份文档里唯一一个**明确承认自己无法自证**的任务。
> 把这件事写出来，比造一个看起来严密的闭环更有价值。

### 9.2 环境自伤风险（本任务最高）

**A11 是唯一会主动修改用户代码的任务。** 三条硬纪律：

1. **只在 git 干净的工作树上运行**。跑前 `git status --short` 必须为空，
   否则拒绝启动 —— 否则 `revert` 无法区分「探针的变异」与「用户未提交的改动」，
   可能把用户的工作擦掉。
2. **`revert` 必须在 `finally` 中**，且探针进程被 kill 时
   须有兜底（原文备份落在 `workspace/probe/backup/`，
   下次启动时检测到残留备份应告警并提示恢复）。
3. **元测试全部走 `tmp_path`**。绝不在 `repo/` 或 harness 自身注入变异。
   A0 实施期用真实路径探针截断 `workspace/tasks/T1/.state` 的教训适用于此 ——
   而本任务的破坏面比那次大得多：**它改的是源代码**。

> 撰写本文档的实测全部在 `/tmp/a11probe` 完成并已 `rm -rf` 清理，
> 未在本仓库注入任何变异。实施时须保持同样纪律。

### 9.3 红的正确形态

| 验收项 | 红的正确形态 | 假绿风险 |
|---|---|---|
| **7 注入规模受控** | 用 `ast.unparse` 实现时 `diff_numstat` 为 `(3, 4)`，断言 `(1, 1)` 为红 | 只断言「diff 非空」或「文件已改变」—— `ast.unparse` 也满足。**必须断言精确的 numstat 与注释逐字保留** |
| **8 分类正确** | 不做分类时 M1 也被判存活，断言 `captured_by_tests is True` 为红 | 断言写成「M1 与 M2 的分类不同」而不指定各自的值 —— 反了也能过 |
| **10 对照组无反应** | **这条的期望是「未检出」** | **断言方向极易写反**：直觉会写「注入缺陷后应检出」，但对照组的正确结果是 `route.target == "05-archive"`。写反了会让基线永远采不到，且看起来像改造前就已经很好 |
| **11 改造后检出** | 三轨任一未接通时 `route.target` 仍为 `05-archive`，为红 | 只断言「攻击者产出了反例」而不看 `route` —— 反例可能是 `inferred` 而不触发返工（A9 的 3.2），机制看似工作实则空转 |
| **12 失败模式不重叠** | M3 若主要由攻击者捕获，断言「由 A8 捕获」为红 | 断言「至少一轨捕获」—— 那样两轨完全同质也能过，A8 的独立价值测不出 |
| **13 M8 被驳回** | A8 若信了自报数值，断言 `refuted` 为红 | 断言 `status != "verified"` —— `unverifiable` 也满足，但那是「校验不了」不是「驳回」。**必须断言等于 `refuted`**（与 A9 验收 11 的同名陷阱同源） |
| **14 探针失效自检** | 探针把「注入失败」报成「审查无效」时为红 | 只测正常路径，从不构造失效样本。**这正是 1.4 那四种形态存在的理由** |
| **3 revert 幂等** | 实现若用「反向 patch」而非「恢复备份」，二次 revert 会把变异再改回去，为红 | 只 revert 一次 |

### 9.4 特别提醒：第 10 条的断言方向

这是本文档最容易写错的一条。对照组（改造前）的**正确结果是「没检出」**：

```python
# 对照组：注入存活变异后，改造前的 reviewer 应当毫无反应
assert baseline["route_target"] == "05-archive"   # 缺陷被放过 = 基线正确
assert baseline["detection_rate"] == 0.0
```

直觉会想写「注入了缺陷就该检出」，于是把对照组也断言成 `03-coding` ——
那条断言在改造前必然失败，实施者会误以为「基线脚本有 bug」而去改脚本，
**最终把基线采成一个假的高分**，第 11 条的对比就失去意义。

**基线采集脚本的注释里必须写明：这里期望的是「未检出」。**

### 9.5 单调性

本任务**不改变任何生产行为** —— 它是离线诊断工具。
因此单调性风险主要在两处：

1. **探针残留**：变异未 revert 会污染用户代码，
   表现为「莫名其妙的测试失败」。9.2 的三条纪律是防线。
2. **元测试的样本文件**：`tests/probe/` 下的夹具若被主套件收集，
   可能产生意外失败。与 A7 的 2.1 同源问题 ——
   夹具须放 `tmp_path` 或明确的非收集目录。
