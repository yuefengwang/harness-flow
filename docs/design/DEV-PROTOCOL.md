# 开发协议：以软约束形式执行红绿准出范式

> 适用范围：`docs/design/` 下全部任务文档（A0-A11）的实施过程。
> 性质：**软约束（prompt-level discipline）**。harness-flow 自身尚未建成
> R1/R2 的硬机制（`red_witness`、证据不可伪造），因此这些纪律**由执行者自觉遵守**，
> 没有程序强制。
> 依据：`docs/self-verification-gaps.md` 的 R1、R2、R12 与准出分级 L1-L9。

---

## 0. 为什么现在就要遵守

我们正在建的机制，是为了让 AI 开发不能自欺。**在建成之前，我们自己写这套机制的
过程同样可能自欺** —— 写一个 `assert True` 的测试、声称"修好了"而没验证过、
改测试让它变绿。这些行为在 A0-A11 的开发中一样会发生。

因此：**先按最终形态的纪律手动执行一遍。** 两个好处：

1. 避免用一个未经自校验的实现去构建自校验机制。
2. 手动走一遍能暴露机制设计里不合理的地方 —— 如果人自己都难以遵守，
   那自动化后 agent 更做不到。

---

## 1. 红绿准出（对应 R1，硬机制建成前的手动版）

每个任务的每个可测子项，按以下顺序执行，**不得跳步**：

| 步 | 动作 | 必须留下的证据 |
|---|---|---|
| 1 | 写测试，**先不写实现** | 测试文件已提交 |
| 2 | 运行测试，**确认它是红的** | 粘贴失败输出（含失败断言原文） |
| 3 | 确认红的原因是**断言失败** | 非 `ImportError` / `SyntaxError` / collection error |
| 4 | 写实现 | — |
| 5 | 重新运行，确认转绿 | 粘贴通过输出（含 passed 计数） |
| 6 | 确认测试文件**未被修改** | 步 1 与步 5 之间测试文件内容一致 |

### 1.1 第 3 步为什么不能省

一个引用不存在模块的空测试也会"红"。若把这种红当作有效的 Red，
整套机制形同虚设 —— 实现只要让 import 成功就能转绿，而断言从未真正被检验。

**判定**：失败输出里必须出现具体的断言失败信息，
而不只是 `ModuleNotFoundError` 或 `E   ImportError`。

### 1.2 第 6 步为什么不能省

「改测试让它过」是最常见的自欺路径。若实现过程中发现测试写错了，
**必须显式声明并回到步 1 重做**，不得在步 4 之后静默修改测试。

---

## 2. 报告纪律：三态，不得二态化

汇报任何结果时使用三态，禁止把「未验证」说成「已完成」：

| 态 | 用法 | 措辞要求 |
|---|---|---|
| ✅ 做到了 | 有可复现的执行证据 | 附命令与输出 |
| ❌ 没做到 | 已尝试且失败 | 附失败原因 |
| ❓ 不确定 | **无法验证 / 未验证 / 缺少判据** | **必须说明为什么无法验证** |

禁止的表述：

- 「应该可以了」「理论上没问题」「大概是这样」→ 全部归入 ❓，并说明原因。
- 「测试通过」但未实际运行 → 这是虚假陈述，不是 ❓。
- 用「基本完成」掩盖有未通过的子项 → 必须列出 ❌ 项。

> `unavailable`（无法执行）**不算通过**。这条与 A6 的 3.3 同构 ——
> 我们要求程序做到的事，自己先做到。

---

## 3. 自循环纪律（对应 R12）

连续多轮修同一个问题时，四条约束：

1. **判据在循环外**：修 bug 前先确定判据（哪条测试、什么输出算对），
   **不在修的过程中调整判据**。
2. **每轮必须产生新信息**：一轮之后若没有得到新的失败信息或新的反例，
   说明在重掷骰子 —— **停下来，把情况交给用户**，不要继续试。
3. **单调性**：已经通过的测试不许变红。若某次改动让既有测试变红，
   优先恢复单调性，不要带着回归继续往前。
4. **逃逸带证据**：放弃或求助时，交出累积的证据（尝试过什么、各自的失败原因），
   而不是只说"搞不定"。

> 第 2 条最容易违反。反复用不同写法试同一个地方而没有新信息，是无效循环。

---

## 4. 证据纪律（对应 R2 与 L6）

- 声称某命令通过时，**实际运行过它**。引用的输出必须是真实执行结果。
- 不修改验证脚本使其通过。若脚本本身有问题，显式说明并单独修。
- 涉及 `.state` / `facts/` 等状态文件时，走既有受控入口
  （如 `stage_state` 的读写函数），不手工编辑。

---

## 5. 范围纪律（对应 hook-03-01 / hook-04-01）

- 只改任务范围内的文件。发现范围外的问题**记录但不顺手修**。
- 不做未被要求的重构。
- 遇到不是自己产生的改动（用户的、其他任务的）**不回退**。

---

## 6. 交付前自检清单

每个任务完成时逐条核对：

```
[ ] 每个可测子项都走过完整的红→绿流程，红是断言失败
[ ] 测试文件在实现之后未被修改（或已显式声明重做）
[ ] 全部既有测试仍通过（单调性）
[ ] 报告使用三态，❓ 项均说明了无法验证的原因
[ ] 引用的所有命令输出均为真实执行结果
[ ] 改动范围未超出任务边界
[ ] 该任务文档的「验收标准」逐条对照过，未通过项已标 ❌ 或 ❓
```

---

## 7. 与硬机制的对应关系

本协议每条都对应一个将来会自动化的检查。落地后软约束自然被硬约束取代：

| 本协议 | 将来的硬机制 | 归属任务 |
|---|---|---|
| 第 1 节 红绿六步 | `red_witness`：哈希冻结 + 断言失败校验 | **A2** |
| 第 2 节 三态报告 | 达成度报告的 done/undone/unknown 判定 | **A10** |
| 第 3 节 自循环 | 反例集合去重 + `MAX_REROUTE` 收敛判定 | **A9** |
| 第 4 节 证据 | 事实包由 harness 生成，agent 只读 | **A0 / A3** |
| 第 5 节 范围 | O5 diff 范围检查 | **A6** |

> **手动执行时的摩擦点应被记录**，作为对应任务设计的输入 ——
> 人觉得别扭的地方，往往是机制设计得不合理的地方。
