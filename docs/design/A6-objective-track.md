## 1. 核心主张

04-review 现在把两件事混在一个 agent 里：客观核查与主观判断。
**客观核查完全不需要 LLM** —— 构建过没过、测试绿没绿、覆盖率多少、
有没有越界改动，这些都是确定性的程序判定。

让 LLM 参与客观判定有害无益：

- 它可能把「测试失败」读成「测试基本通过」。
- 它的结论不可复现，同一份输入两次运行可得不同答案。
- 它引入了本不存在的不确定性 —— 退出码是 0 或非 0，没有中间态。

> 判据：任何能用退出码或数值比较表达的检查，都不该经过 LLM。

## 3. 必须修复的现存缺陷

### 3.1 O3：测试结果判定只看退出码（已核实）

`hooks/lib_run_tests.sh` 的 `run_project_tests()` 仅判断 pytest 是否非零退出。
**盲区**：「全部 skip」时 pytest 返回 **0**，会被判为通过。

> ⚠️ **A3 的实测修正了本节原有的一处断言**（见 A3 的 2.3）：
> 原文称「收集到 0 个测试」与「全部 skip」两种情况**均返回 0**。
> 实测只有后者成立 —— **零测试的退出码是 5**（`no tests ran`）：
>
> | 场景 | 退出码 |
> |---|---|
> | 正常套件（2 passed, 1 skipped） | 0 |
> | 零测试 | **5** |
> | 全部 skip | 0 |
>
> 这不削弱 O3 的必要性，因为**有一个更前置的缺陷让退出码 5 永不出现**：
> `run_project_tests()` 在无 `pytest.ini` / `pyproject.toml` / `test_*.py`
> 时**整段跳过并 `return 0`**，pytest 压根没跑（A3 的 2.4）。
> 即「没测试」当前不是被误判，而是**根本没被检查**。
>
> **验收断言必须按真实退出码写**：构造零测试目录时断言 `exit_code == 5`。
> 若照原文写成 `== 0`，测试本身就是错的。

这是当前最廉价、最有效的一个修复 —— 一个没有任何测试的项目现在能通过测试门禁。

**改法**：取 collected / passed / skipped 计数，写入 `facts/tests.json`
（**采集由 A3 负责**，本任务只消费），并判定：

> ⚠️ `--json-report` **不可依赖**（A3 的 2.6 实测）：本机未安装
> `pytest-json-report`，且 hook 跑在**用户仓库的解释器**上
> （`_project_python()` 优先用 `target_dir/.venv/bin/python`），
> 更不能假定插件存在。A3 改为解析摘要行，解析失败记 `parse_status: "unparsed"`
> 并保留原文 —— **不猜数字**。本任务遇到 `unparsed` 时按 `unavailable` 处理。

```
collected == 0                    → 失败：无测试
skipped == collected              → 失败：全部跳过
skipped / collected > 阈值(0.5)   → 警告
```

### 3.2 严重性判定不得依赖 Route（消除循环依赖）

`hooks/check_04-review.sh` 现有逻辑中，README 缺失在归档路由时是错误、
返工路由时是警告。这形成「Route 决定严重性、严重性又决定 Route」的循环。

**定案**：客观轨一律按**最严标准**判定，与 Route 无关。
返工时的宽容由仲裁器的优先级顺序体现（已在返工路径上，不会因 README 再次返工）。

### 3.3 禁止「找不到就跳过」

现有代码里反复出现该模式，且已造成多次误判（`check_04-review.sh` 与
`lib_run_tests.sh` 的历史注释均有记录：target_dir 为空则静默跳过全部 README 校验）。

**规则**：前提缺失时必须区分三态，不得二态化：

| 状态 | 含义 | 处置 |
|---|---|---|
| `pass` | 检查执行且通过 | 通过 |
| `fail` | 检查执行且未通过 | 失败 |
| `unavailable` | 检查**无法执行**（工具缺失、前提不满足） | **记录为 unavailable，不算通过** |

`unavailable` 项进入 A10 报告的「不确定」分类，而非静默计为成功。

## 4. 输出契约

客观轨产出结构化结果，供 A9 仲裁器消费。**不产出自然语言结论**：

```jsonc
{
  "checks": [
    {"id": "O2", "name": "tests", "verdict": "pass", "detail": "25 passed"},
    {"id": "O3", "name": "test_validity", "verdict": "fail",
     "detail": "collected=0", "severity": "high"},
    {"id": "O8", "name": "coverage", "verdict": "unavailable",
     "reason": "diff-cover 未安装"}
  ],
  "hard_fail": true,
  "hard_fail_ids": ["O3"]
}
```

`hard_fail` 为 true 时，A9 仲裁器命中优先级 1，直接 route 到 03-coding。

## 6. 验收标准

1. 一个**零测试**的项目被判 O3 失败（当前会通过）。
2. 一个**全部 skip** 的测试套件被判 O3 失败。
3. README 缺失在返工路由与归档路由下判定结果**一致**（无循环依赖）。
   > 实体位置已由 A9 的 3.3 定位：`check_04-review.sh:153` 的
   > `if [ "$ROUTE_VAL" = "05-archive" ] && [ "$README_ERRORS" -gt 0 ]`
   > 就是那个循环依赖，**由 A9 负责删除**。
4. diff-cover 未安装时 O8 记为 `unavailable`，**不计为通过**，且不阻断。
5. 越界改动（`target_dir` 外的文件）被 O5 捕获。
6. 输出的 JSON 中 `hard_fail_ids` 与实际失败项一致。
7. 客观轨执行过程**零 LLM 调用**（可用调用计数断言）。
8. 现有通过的任务在改造后仍通过（除新增检查确实发现问题者）。

## 9. 本任务的红绿要点（含自指风险）

### 9.1 自指风险

本任务实现的是「检测测试是否有效」的检查（O3）。
**如果用无效的测试来测试它，就是用要防的错误来验证防错机制。**

因此 O3 的测试必须构造**真实的负样本目录**：

| 负样本 | 期望判定 |
|---|---|
| 目录内无任何测试文件 | O3 fail，`detail` 含 `collected=0` |
| 测试全部标 `@pytest.mark.skip` | O3 fail |
| skip 比例超阈值 | O3 warn |
| 正常测试套件 | O3 pass |

**不接受 mock 掉 pytest 输出的做法** —— 那测的是解析逻辑，不是检查逻辑。
必须真实运行 pytest 于临时目录。

### 9.2 红的正确形态

| 验收项 | 红的正确形态 | 假绿风险 |
|---|---|---|
| O3 零测试 | 在**当前代码**上运行该测试应通过（因为现在会误判为 pass），改造后应变为 fail 检出 | 反向：这是少见的「改造前绿、改造后红」，须注意断言方向 |
| 循环依赖消除（3.2） | 同一 README 缺失状态在两种 Route 下断言判定一致，改造前应不一致 | 只测一种 Route |
| `unavailable` 三态 | 断言 verdict 为 `unavailable` 而非 `pass`，改造前会是 pass | 断言「不是 fail」而漏掉与 pass 的区分 |
| 零 LLM 调用 | 用调用计数器断言为 0，人为注入一次调用应能让它红 | 从不验证计数器本身有效 |

> 第一行值得特别注意：O3 的语义是「让原本假通过的场景变为失败」。
> 断言应写成「零测试的项目**必须被判失败**」，在改造前这条断言会红 ——
> 这才是正确的 Red。

### 9.3 单调性

O3 上线会让部分存量任务失败。按协议第 3 节第 3 条，须先区分：

- **真实检出**（那些任务确实没有有效测试）→ 预期行为，不算回归。
- **误判** → 必须修。

两者必须逐个分辨，**不得用放宽阈值的方式让存量任务变绿** ——
那正是本机制要防的行为。
