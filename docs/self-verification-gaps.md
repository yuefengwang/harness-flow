# 自校验缺口与修正点清单

> 状态：**待逐条确认**。基于源码核查（2026-08-23）产出。
> 用途：本文件是讨论底稿，每条修正点独立编号，确认后再进入实现。
> 讨论起点：「AI 容易写出只有花架子的应用，自校验为何失效」。

---

## 0. 核心结论

把「自校验难」拆成两个**性质完全不同**的命题，是后面所有判断的前提：

| | 命题 | 可否机械检测 | 结论 |
|---|---|---|---|
| A | **业务真理缺失**：AI 不知道「审批要不要跳过财务」 | 否 | 只能外部输入，不可消除。但可**一次输入、多次复用** |
| B | **内部一致性缺陷**：函数体是 `pass`、断言是 `assert True`、mock 泄漏到生产路径 | **是** | 不需要业务真理即可判定。**当前门禁完全没有检测** |

「花架子」主要属于 B，而 B 是可以自动抓的。当前 harness 抓不到，原因不是模型能力，
而是**判据可被产出方伪造 / 判据与产出的错误分布高度相关**。

这与 `docs/design-json-state-source.md` 里已经写下的那句话是同一个道理：

> 「歧义是消不掉的，只要边界可被内容伪造。」

对证据同样成立 —— **只要判据可被产出方伪造，校验就是装饰**。

## 1. 已核实的现状缺口

每条均附源码证据。编号 `F*` = Finding。

### F1. reviewer 与 developer 共享上下文（已核实）

- **证据**：`sw_lib/prompts/builder.py:63` 调用 `_read_previous_stage()`（定义在 :116），进入 04 阶段时
  将整份 `03-coding.md` 作为「前一阶段产出」注入 reviewer 的 prompt。
- **后果**：该文件含 developer 自己写的 `Implementation Notes` / `Decisions` / 自签的 Gate。
  reviewer 不是独立看代码，而是**先读被告陈情书再看卷宗**。developer 的错误假设
  被以权威文档的形式显式传递。
- **注**：这一条与「LLM 无状态」无关，是 prompt 组装层面的真实上下文共享。

### F2. 错误分布相关（设计层判断，非 bug）

- **证据**：`config/config.yaml` 中 analyst / architect / developer / reviewer / archivist
  五个角色全部为 `opencode/mimo-v2.5-free`。
- **论点**：LLM 无状态保证了**独立采样**，但不保证**独立犯错**。同一 checkpoint 在
  相似 prompt 下错误分布高度相关：developer 漏掉边界条件是因为该条件在其先验中
  不显著；reviewer 是同一组权重、同一先验，该条件对它同样不显著。
- **推论**：换 provider 做 reviewer 有效（权重不同）；让同模型再看一遍基本无效。
- **措辞修正**：上轮我称之为「自问自答」不准确，准确说法是**错误相关性高**，
  而非记忆共享。

### F3. Red→Green 无任何强制机制

- **证据**：`hooks/03-coding.md` 的 `hook-03-02` 要求 "Red → Green required.
  Never assume fixes."，但 `hooks/check_03-coding.sh` 中没有任何对应实现。
  `templates/03-coding.md` 的 Red / Green 是两个由 agent 自填的复选框。
- **后果**：红灯是否真的亮过，完全依赖 agent 自述。

### F4. 测试文件可被随意改写，无冻结

- **后果**：「改测试让它过」是最常见的花架子手法，当前无任何拦截。

### F5. 测试结果判定只看退出码

- **证据**：`hooks/lib_run_tests.sh` → `run_project_tests()` 仅判断 `pytest` 是否非零退出。
- **盲区**：「收集到 0 个测试」与「全部 skip」两种情况 pytest 均返回 **0**，会被判为通过。

### F6. `.state` 保护可绕过（安全洞）

- **证据 1**：`sw_lib/tools/toolbox.py:129` 用 `target.name in (".state", "STATUS.json")`
  拦截写入 —— 仅匹配文件名。
- **证据 2**：`sw_lib/tools/toolbox.py:182`，`restricted` 检查是字符串匹配
  `".state" in command`，可通过拼接绕过。
- **证据 3**：`DEFAULT_ALLOWED_COMMANDS`（`toolbox.py:24`）包含 `python` / `python3` /
  `sh` / `bash` / `zsh` / `sed`。
- **后果**：agent 可通过 `python -c` 或 `sed` 写任意文件，包括 `.state` 与 `hooks/` 自身。
- **重要性**：这是后续所有「证据链」机制的地基。**地基漏了，上层全部失效**。

### F7. 02 阶段的 `Verify` 字段从未被执行

- **证据**：`hooks/02-planning.md` 的 `hook-02-01` / `hook-02-04` 只要求
  "Do + Verify present"；`hooks/check_02-planning.sh` 只 grep `## Task DAG` 与
  `## Test Strategy` 两个标题是否存在。
- **后果**：`Verify` 是自由文本，写什么都行，从未被当作命令运行过。

### F8. 模板与 hook 对 Route 的规定互相冲突

- **证据 A**：`templates/04-review.md:18` —— 「根据分析判断直接填写 Route，**无需等待用户确认**」
- **证据 B**：`hooks/04-review.md` 的 `hook-04-07` —— 「agent **不得**自行填写 Route 值，
  必须通过 `ask_user` 确认」
- **后果**：agent 同时读到两份（builder 会注入模板与 hook 两者），而**模板那份是宽松的一方**。
  需定哪个作准。

### F9. 01 阶段产出全为散文，无可执行验收

- **证据**：`templates/01-brainstorming.md` 的产出为 Ambiguity Score、Clarifying
  Questions、Pre-mortem、ADR —— 全部是自然语言，无一行可执行。
- **后果**：需求对齐的结果无法参与任何自动校验。

### F10. oracle 成本不递减

- **证据**：`docs/EVOLUTION.md` 当前是一张空表 + 一行示例。
- **后果**：每次人工发现一个花架子，判据没有沉淀成自动检查，下个任务需重新支付
  同一笔人工校验成本。规模上永远不划算。

### F11. 「等待外部审批」被伪装成「正在工作」（已修复，2026-08-23）

- **事故**：任务 `newtask`（02-planning）卡死 26 分钟。用户的第一判断是
  「opencode 免费模型限额了」—— 判断错误，但**这个错误完全是 UI 造成的**。
- **因果链**：`templates/02-planning.md:3` 写着 `> Hooks: hooks/02-planning.md`
  → agent 被路径引用诱导，`glob **/hooks/*.md` 越出 workdir
  → opencode 的 `external_directory` 判定无匹配规则 → 默认 `ask`
  → harness 不订阅 `permission.asked` → 双方互等到 `CHAT_TIMEOUT`(1800s)。
- **要点**：全程 UI 显示「Agent 正在处理中」。技术上没说错，但它把
  **「阻塞等待外部输入」和「正在计算」压成了同一个状态**。用户无法区分
  「在算」「在等我」「已经死了」，只能猜 —— 于是猜错。
- **一般化教训**：凡是 harness 会**等待外部事件**的地方，状态机就必须有一个
  与「工作中」区分开的显式态，并且要说清**在等什么**。这不是锦上添花：
  没有这个态，任何一次死锁都会表现为「很慢」，而「很慢」不会触发排查。
- **修复**：三层，见 `sw_lib/agents/opencode.py` 的 `_ASK_CAPABLE_PERMISSIONS`
  与 `_on_permission_asked`、`transport.start_events` 的 `on_permission`、
  以及 `builder._read_hook_rules` 的内联声明。
  实测对照组（无底规则、不应答）精确复现挂死；实验组 `asked=0`，
  仅第二层（订阅 + 自动应答）也能独立解锁。

### F12. harness 把自己的 `INSTRUCTIONS.md` 注入被开发项目的 agent（未修）

- **证据**：`sw_lib/prompts/builder.py` 的 `_read_global_rules()` 按
  `INSTRUCTIONS.md` → `PROJECT_RULES.md` → ... 顺序探测 **harness ROOT**，
  命中即整份注入，段标题为「全局项目规范」。
- **实测**：01-brainstorming 阶段 prompt 共 20588 字符，其中绝大部分是
  harness **自身**的架构文档 —— 含完整目录树（`sw_lib/`、`templates/`、
  `hooks/`）、模块清单、以及诸如
  「`read_state()` lives in `sw_lib/core/state.py`」这类 harness 内部实现细节。
- **双重后果**：
  1. **语义错位**：被开发的项目（`repo/<task>`）拿到的是**工具的**开发规范，
     不是它自己的。任务 agent 被告知要遵循 harness 的模块划分。
  2. **越界诱导面**：F11 只修掉了模板里那一行路径引用，而这份文档里的
     harness 内部路径**数量级更大**，每一条都是一次 `external_directory`
     判定的邀请函。F11 的第一层底规则兜住了它，但诱导源仍在。
- **为何未修**：修法要区分「harness 自身开发规范」与「被开发项目的规范」，
  即 `_read_global_rules` 应探测 `target_dir` 而非 harness ROOT。
  这会改变所有阶段 prompt 的内容，影响面远超 F11 的 ask 死锁修复范围，
  按 DEV-PROTOCOL 范围纪律记录而不顺手修。
- **相关测试**：`tests/unit/prompts/test_prompt_self_sufficiency.py` 中
  `test_prompt_stage_sections_contain_no_harness_paths` 的 docstring 记录了
  断言范围为何被收窄到「当前阶段模板」「强制规则」两段。

### R1. Red 见证机制

**原则**：红不是 agent 声称的状态，是 **harness 亲自观测并留痕的事件**。

1. 03 阶段拆为 `03a-test` / `03b-impl` 两个动作。03a **只允许写测试文件**，不许碰实现。
2. 03a 结束时由 **harness 自己**跑测试（不经 agent），要求：
   退出码非零 **且** 失败节点集合非空。将该集合 + 每个测试文件的 `sha256`
   写入 `.state` 的 `red_witness`。
3. 03b 允许写实现。准出时 harness 重跑，要求：
   `red_witness` 中所有节点转绿 **且** 测试文件哈希**未变**。
   哈希一变即拒绝 —— 直接掐死「改测试让它过」。
4. **防伪造补充**：03a 的失败原因必须是**断言失败**，不能是 `ImportError` /
   `SyntaxError` / collection error。否则 agent 写一个引用不存在模块的空测试
   就能「造红」。这一条容易漏，缺了整套机制形同虚设。

### R2. 证据存储不可伪造

`red_witness` 若存在 agent 可写的位置则无意义。二选一或并用：

- 收紧 `run_command`：白名单移除或包装 `python` / `sh` / `bash` / `sed`；
  把路径保护从「字符串匹配命令」改为「对实际写入路径做校验」。
- 给 `.state` 中的证据字段加 HMAC，harness 持密钥，校验时验签。

> 这是 R1 的**前置条件**，不能后置。

### R3. 测试有效性检查

- 收集到的测试数必须 > 0。
- 不允许全部 skip（或 skip 比例超阈值即拒）。
- 引入 diff coverage（`diff-cover`）：卡本次 diff 新增行的覆盖率。便宜且不可辩驳。

### R4. 变异注入（穷人版变异测试）

把本次 diff 涉及的新函数体自动替换为 `raise NotImplementedError`，
断言测试套件**必须转红**。若仍绿 → 测试是摆设。

- 纯机械，零业务知识，是抓花架子**信噪比最高**的单项指标。
- 约 30 行 hook 即可实现。成熟工具可后续替换为 `mutmut` / `cosmic-ray` / `Stryker` / `PIT`。

### R5. 桩 / mock 泄漏检测

生产路径静态扫描：无 `pass` / `...` 空函数体、无硬编码返回值、无 mock 泄漏。

### R6. reviewer 上下文隔离

> **已细化为独立设计文档**：`docs/design-reviewer-independence.md`（v2，2026-08-23）。
> 该文档将本条从「上下文隔离」扩展为**三轨审查**：客观轨归 hook 脚本，
> 攻击轨产出可执行反例，设计轨产出可交叉校验的设计意见；三轨经 Route 仲裁器合并。
> 同时覆盖 F1 / F2 / F8 与 R7。
>
> 核查中的两项重要发现：
> 1. reviewer 的 prompt 里**完全没有 diff**（`grep -rn "diff" sw_lib` 零结果），
>    即「该有的没有」比「不该有的有了」更严重。
> 2. **R6 单独实施无法解决「自问自答」**。自校验失效有三个成因：
>    C1 上下文污染、C2 先验相关、C3 判据缺席。R6 只解决 C1、缓解 C2；
>    **C3 是根本，必须靠 R1（测试冻结前置）与 R8**。
>    因此 **R1 的实施顺序必须早于 R6** —— 本清单原先把 R1/R8 与 R6 平列，
>    未体现这个依赖。

- 修改 `builder.py`，使 04 阶段**不注入** `03-coding.md` 的叙述部分。
  reviewer 的输入应为：**规格 + 冻结的测试 + diff**。
- reviewer 的产出**不应是意见，而应是反例** —— 一个能让代码出错的具体输入。
  反例可验证，「看起来没问题」不可验证。
- **自检方法**：拿 R4 变异注入过的代码喂现有 reviewer，看它抓不抓得到。
  抓不到 → 它是橡皮章。

### R7. 异构 reviewer

`config.yaml` 中让 reviewer 使用**不同 provider / 不同权重**的模型。
依据见 F2：同权重再看一遍无效。

### R8. 可执行验收场景（补 A 类，上轮遗漏）

> 上轮给出的防伪造条目全部只保证「代码不是空壳」，**不保证它有用**。
> 一个通过全部防伪造检查的实现，可以完美实现一个没人需要的功能 ——
> 这正是「需求没对齐下的花架子」，它在结构上无法被内部一致性检查抓到。

- 从 01 阶段起，每条需求必须落成**端到端可跑的场景**：输入、操作、期望输出。
- 由 harness 执行，**不经过 agent 手写的单测**。
- 区别：单测测「我以为的逻辑」，场景测「用户要的结果」。

### R9. `Verify` 可执行化

`02-planning` 每条任务的 `Verify` 必须是**可执行命令**，且准出时按 node id
实际命中执行。当前它只是被要求「存在」（见 F7）。

### R10. oracle 成本单调递减

每次人工发现的花架子，判据必须沉淀为一条**永久自动检查**。
`docs/EVOLUTION.md` 位置正确，但应从「给人看的复盘散文」改为**不断增长的检查集 / 测试语料库**。

> 这条比任何技术项都要紧：它决定自动化到底省不省力。

### R11. Route 规定消歧

F8 的两处冲突择一作准，另一处改写。成本极低，建议先做。

### R12. 自循环准入四条

一个循环能放心无人值守跑，需同时满足：

1. **判据在循环外**，且 agent 不可写（= R2）。
2. **每轮必须产生新信息**（新反例或新红灯），否则是重掷骰子，应升级给人。
3. **单调性**：已通过的判据不许变红。这是长循环能跑的前提。
4. **逃逸带证据**：退出时交出累积证据，而非静默停止。

当前 `AUTO_ADVANCE_MAX_STAGES` 是第 4 条的粗糙版；前 3 条尚无。

## 4. 业界成熟做法（参考）

学术上称 **test oracle problem**（Barr 等，2015 年有综述）。
工业界的可靠答案是同一个套路：**把判据挪到 agent 写不到的地方**。

| 做法 | 说明 | 是否需业务真理 |
|------|------|--------------|
| 隐藏测试 | SWE-bench 系 harness 的 `FAIL_TO_PASS` / `PASS_TO_PASS`，agent 全程看不到判据。**最稳** | 需（但只需一次） |
| 变异测试 | `mutmut` / `cosmic-ray` / `Stryker` / `PIT`。改坏实现测试仍绿 = 测试是摆设 | **否** |
| 差分测试 | 有老系统就用老系统当 oracle，业务真理免费获得 | 否（若有老系统） |
| 契约驱动 | OpenAPI + `schemathesis`、Pact。契约是外部真理，测试由 schema 生成而非手写 | 需（一次） |
| 属性 / 不变量 | `Hypothesis` 等。人给不变量比给完整规格便宜得多，且机器可查 | 需（一次，廉价） |
| diff coverage | `diff-cover` 卡新增行覆盖率 | 否 |

**LLM-as-judge** 只适合做分诊过滤，已知可被优化掉，**不应作为门禁**。

---

## 5. 关于 Loop-Engineering

- 它**不是**一个有公认定义和成文准出标准的方法论，是「生成 → 执行 → 观测 → 修正」
  这类闭环实践的**松散统称**。
- 它**不解决**本文的问题，**它放大判据**。循环的收敛点由 oracle 决定，
  循环质量只决定收敛速度。
- **判据弱的循环跑得越久，产出的花架子越精致** —— 因为它在优化「通过检查」这个目标，
  而检查恰好抓不到实质。

> 结论：先修判据，再谈自动化程度。

---

## 6. 一句话总结

- **防伪造**（R1–R5）让 AI **不能骗你**。
- **可执行验收**（R8）让 AI **不能跑偏**。
- **业务真理**仍然只能从人这里来 —— 但它可以**只输入一次，然后被复用无数次**（R10）。

这是唯一能让自动化真正省力的路径。
